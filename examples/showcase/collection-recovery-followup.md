# 本地取证、失败渠道与人工交接优化（2026-10-15）

本轮修复接入显式 `review_driven` 试验路径，标准 `legacy` 仍默认。五个冻结合成场景各运行两条流程一次，规划、草稿与复核全部调用真实模型生成，无预置反馈、无回复回放。新编排补到了磁盘和缓存场景的本地资源证据，在两个来源失败场景中停止了重复规划并形成可执行的人工核查待办；推理措辞与反证范围仍有残留问题。

## 实现与职责

| 模块 | 职责与边界 |
| --- | --- |
| `app/workflow/collection_recovery.py` | 根据实际查询台账区分未查询、已查询和渠道失败；生成登记本地边界的有限检查，识别已失败的补查渠道。没有案例ID、参考答案或根因判定。 |
| `app/workflow/coordinator.py` | 接入新路径的首次本地检查、复核后分流与预算门禁；程序检查仍走原计划校验、执行器和任务台账。通用本地补查不能替换明确的外部信息需求或已有有效定向检查。 |
| `app/workflow/collection.py` | 同一批或后续任务中，已明确失败的渠道不再因换类别/过滤而重复读取；记录 `planned_check_channel_blocked`，不把未执行检查伪造成失败记录。 |
| `app/agents/contracts.py`、`app/workflow/review.py` | 新Reviewer可用 `request_source` 标识所需本服务渠道，而非规划参数或授权执行。校验请求存在、角色工具范围、日志类别归属及外部边界；原ReviewDecision不增加字段。 |
| `app/workflow/handoff.py` | 保留原查询参数和真实失败；生成 `recovery_tasks`，包含所需记录、完成条件、负责人状态及变更审批边界。不能把程序待办当成模型已复核建议。 |

首次取证后，对未尝试的登记 `resource/configuration` 日志做一次基线检查，最多两项、无level/error_code限制。保留原任务/工具/模型/时间上限，并留一个工具位置给后续定向补查；不能执行时带现有观测进入判断，不增加额度。状态核查和已经启用的诊断包不叠加此批次。空结果只证明所查类别/窗口没有匹配记录，不证明健康；问题状态仍由Diagnosis和Reviewer判断。

本地程序任务使用内部 `LocalBoundaryTask` 保存来源，工具事件标记 `program_registered_boundaries`，不会把程序补查标成模型自主选择。模型提出的其它计划仍标记 `validated_supervisor_plan`。

渠道失败只采用明确的通道级代码：SOURCE_UNAVAILABLE、SOURCE_NOT_CONFIGURED、AUTH_ERROR、QUOTA_EXCEEDED。类别未登记、空结果、截断和普通超时不能扩大成整个渠道不可用；若后续实际查询成功，则解除旧失败标记。已有新的有效查询提示不会被失败渠道快捷分流吞掉。

Reviewer仍给出真实机制缺口。程序用已验证的渠道提示和实际失败台账将重复补查路由为 `source_recovery_required`，省掉无增量的Supervisor规划。这个路由保留partial和未解决问题，不把“渠道失败”变成业务根因，也不自动支持假设。缺少明确渠道提示时保留原规划路径，不从自由文本猜出工具或原因。

交接分开记录两种行动：`reviewed_actions` 是模型提出并复核的建议，`recovery_tasks` 是程序依据失败台账生成的人工待办，明确 `model_reviewed=false`。后者要求核查最近成功查询、渠道与登记接入状态，取得原工单范围的实际观测，或提供带对象/时间/来源的人工替代观测。任何凭据、接入配置或服务变更另行审批，不自动恢复、不关闭工单。

负责人只来自实际已查询的owner证据。已有服务负责人可以协调人工交接，不等于已确认其拥有观测平台权限；没有负责人时保留null并要求人工确认，不补入隐藏fixture中的团队。

## 验证方法与来源

- 验证应用指纹：`f8d1be132b192cf7`；本批十轮期间应用、脚本和冻结输入保持不变。
- 模型：本地配置 `qwen3.7-flash`，两边相同的temperature=0、输出上限2200、请求超时30秒、SDK重试0。
- 原三个场景：fresh_001、fresh_002、fresh_003，使用原冻结标准。补充既有冻结案例eval_005（指标与日志不可用）、eval_008（缓存上限变化与淘汰）；对应参考答案和rubric另行校验哈希，不发送给模型。
- 每场景每流程一次，轮换先后顺序；16次模型调用、8次工具调用、360秒，预留3次模型调用和20秒收尾。每轮独立16次封装层请求尝试上限，十轮总上限160次，实际42次；没有单臂专用末稿付费预留。
- 全部合成快照，两边使用同一Provider和授权边界，自主选择的实际观测可能不同。程序取证、非盲审、默认反证保护均相同，无种子模型、固定首稿/复核或历史回复回放。
- 这些是已见开发案例，不是独立未见保留集；标准作者在运行后检查质量，无独立人工评分。没有按结果改代码、重跑到通过或排除失败。

机器记录：[collection-recovery-validation.json](collection-recovery-validation.json)。计划、每轮查询、角色计数、失败、恢复分流、末稿和来源哈希均保留。原始十份报告与十份请求记录位于本地 `output/orchestration-autonomous/2fe237df-ee11-47a8-844c-8fbb14c42f87/`，均核对哈希和计数，原始运行数据不提交。上一轮记录[保持独立](orchestration-autonomous-comparison.md)，不能与本轮混成一次验证。

## 真实模型结果

| 场景 | 标准：状态／请求／工具 | 新编排：状态／请求／工具 | 对照发现 |
| --- | --- | --- | --- |
| 001 归档写入失败 | partial / 7 / 3 | completed / 3 / 5 | 新编排取得ENOSPC与零可用字节，支持卷耗尽机制，建议核查容量增长/清理策略；触发未知保留。标准漏查资源日志，补查参数连续两次不合法后结束。 |
| 002 物流TLS失败 | completed / 4 / 2 | completed / 3 / 4 | 标准只查指标与变更，未取得证书日志，笼统交互机制内部通过。新编排取得证书过期日志和本地控制，正确识别近端机制；仍未查发布记录，宽泛反证问题保留。 |
| 003 日志不可用 | partial / 7 / 4 | partial / 3 / 2 | 新编排保留机制未知，直接失败渠道交接；有复核的人工日志核查建议及1个程序恢复渠道任务。标准在建议纠正及补查规划后停止，最终没有有效行动。 |
| eval_005 双渠道不可用 | partial / 3 / 5 | partial / 4 / 4 | 两边安全保留未知并实际取得负责人。标准查询两个日志类别均失败，未进入诊断复核且无最终行动。新编排只尝试一次日志/指标渠道，生成已复核人工待办及2个程序恢复任务；其模型消耗反而多1次。 |
| eval_008 缓存容量变化 | partial / 5 / 2 | completed / 3 / 4 | 标准从指标/变更推测方向，但Reviewer两次引用非法，草稿保持未复核。新编排补足资源日志，支持容量不足、淘汰与命中率下降机制；没有自动扩容或把全部登录延迟归因缓存。 |

新编排十轮中自己的五轮未发生validation_failure，标准五轮有6个事件。仅说明此批样本；不能作为输出可靠性的统计结论。两条流程在来源失败场景保留partial是合理行为，不按completed数量计算准确率。

仍然存在的质量问题：

- 新002依据CERT_EXPIRED反驳整个“本地TLS配置／信任链问题”，范围过宽；没有取得发布记录，不能完整展开10:01故障早于10:06发布的时间反证。标准002内部通过也不代表诊断证据齐全。
- 新003行动条件将日志不可用与变更未查询合写为“不可用或未查询”；程序台账已经正确区分，但模型文字仍不够精确，且建议人工核查附带了审批条件。
- 新eval_005的“监控故障掩盖真实状态”只是观测限制，不是业务故障的竞争机制。末稿保持未确认，没有将其当成业务根因；分类仍可更准确。
- 新eval_008的人工建议偏向核查变更执行和授权细节，已取得变更时间戳却仍泛称“执行时间未知”。建议没有直接承诺扩容，但对宿主机余量及恢复条件的核查不够具体。
- HC任务改善了实际交接包，但其完整性是程序策略的效果，不能计为模型自主生成了这些步骤。没有实际恢复观测渠道或验证业务恢复。

这批模型请求少10次（38.5%）、合并token少24.3%、耗时总和少23.0%，工具调用多3次。所有42次响应有用量元数据，包含标准流程中非法的回复。未发生网络错误或模型付费上限耗尽；封装层 `.invoke` 次数不是已核对的供应商HTTP账单。

只看原三场景，本轮标准18次、新编排9次；上一轮是18次、14次。上一轮与本轮标准模型输出也发生变化，实际观测集合和角色纠正次数不同，不能把跨批差额归因于某一个修复，也不能将这些数字写成普遍成本/延迟收益。

未读取账单或定价/缓存折扣，实际金额仍为null。若输入与输出每百万token单价分别为Pi、Po，忽略其它收费，本批模型费用差额为 `(-35903 × Pi - 2939 × Po) / 1000000`。额外只读查询的真实观测平台成本、延迟与容量压力没有在合成Provider中测得。

## 免费检查与默认行为

755项全量：735通过、20项数据库测试跳过、失败0。67项定向检查通过，包括本地取证不增加模型轮次、不自动支持问题、原预算/未登记类别保护、渠道失败与空结果区分、批次内后续读取阻止、来源提示不授权工具、人工任务保留未知负责人，以及原修稿/范围纠错边界。

标准流程15份行为基线逐一匹配输出、事件、预算与停止原因。新路径的少数工具计数断言相应增加首次本地批次；过期请求测试按新流程完成本地阶段后再检查旧请求拒绝。未放宽引用、协议、权限或修稿范围断言。初次全量发现旧测试跳过新阶段，适配后全量复跑通过；最终日志哈希见机器记录。

前端没有修改或重建；数据库集成仍未实测。没有真实业务修复、生产观测恢复、消息发送或审批。`review_driven_v2` 报告追加 `collection_recovery_policy=local_channel_recovery_v1`，标准请求、报告、默认策略与启动幂等格式保持原行为。
