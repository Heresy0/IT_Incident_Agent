# Agent 编排与 Harness 项目展示

本展示复用实际工作流和工具执行器，提供三条免费控制演示、一组历史真实模型对照和一个人工审批修复案例。模拟结果与模型质量分开报告，不承诺生产级准确率。

## 一条命令复现

安装根目录锁定依赖后，在项目根目录执行：

```powershell
.\.venv\Scripts\python.exe scripts/showcase_incident.py
```

Linux/macOS 或已激活虚拟环境时：

```sh
python scripts/showcase_incident.py
```

不需要模型 Key、访问令牌、PostgreSQL、Docker 或另一个项目。脚本没有 live 开关，不读取 `.env`。输出保存到 `output/showcase/<运行批次>/`；可直接打开 `index.html` 查看，也可读取 `summary.json` 和三份 JSON/Markdown 原始控制报告。重复执行会创建新批次，避免覆盖历史结果。

脚本同时运行已有同预算模拟对照、五类 Harness 约束的七个测试，以及内存中的模拟审批闭环。遇到与预期不符的结果返回非零状态，不通过提高预算消除失败。

## 三条演示及实测结果

2026-10-10，在当前应用源码上执行；全部为脚本模型和合成观测。下表的“模型调用”是脚本调用计数，付费请求为零。

| 演示 | 脚本模型 / 工具尝试 | 结果 | 要观察什么 |
| --- | --- | --- | --- |
| 正常诊断，case_001 | 6 / 2 | completed / passed | Supervisor 选择 Investigation；工具结果进入证据目录，诊断引用当前观测 |
| 复核补查，case_003 | 12 / 5 | completed / passed | 初稿受历史 DB CPU 线索误导；Reviewer 要求当前池指标和日志；执行一次补查后改为连接池候选 |
| 预算不足，case_003 | 8 / 3 | partial / needs_information | 保留终结预算完成复核，拒绝负担不起的补查，以 BUDGET_EXCEEDED 停止 |

三条演示的六项机械检查分别通过：事件序列、调用计数、快照完整性、引用有效性、诊断契约和预算。复核补查必须发生新工具执行，并有两次复核；仅出现补查任务名称不算成功。

默认同预算模拟对照覆盖六个开发案例、十二条链路。两种链路均使用模型调用上限 16、工具尝试上限 8；它只验证对照基础设施，质量状态为 `excluded_scripted`。

本轮免费控制结果可公开核查：[control-result.json](control-result.json)。后端全量回归 239 项，232 项通过、7 项隔离数据库检查按条件跳过，无失败；与三条演示的计数分别报告，不叠加成更多测试成绩。首次沙箱执行停滞后仅终止本次测试进程，在支持本地线程的环境以 60 秒上限重跑，16.442 秒完成；未改业务代码。

五类约束见 [Harness 证据](harness.md)；架构和取舍见 [设计说明](design.md)。

用户授权后执行一次 case_003 配对，qwen-turbo、相同观测和每条 16 模型/8 工具/180 秒上限；没有自动追加运行或修改 Agent。当前应用指纹 `42923fcafc2a4a0c`，提交基点 `b78b4254a1c7c37767b79433d24f0883ccedc95c`，工作区有未提交修改，指纹及 dirty 状态同时记录，不能只用提交号代表本次源码。

公开结果见 [current-comparison.json](current-comparison.json)，逐项辅助审阅见 [current-assistant-review.json](current-assistant-review.json)。原报告及人工评分模板保留在本地 `output/incident-comparison-current/871a7bd0-7606-4710-9f4e-a110524cca58/`。

| --- | --- | --- |

| 模型 / 工具尝试 | 2 / 4 | 6 / 1 |

本组实际付费模型调用 8 次、工具尝试 5 次，费用未知。两条链路各六项机械检查通过，不意味着两者诊断质量等同或全部业务观测覆盖。

单 Agent 查询指标、resource 日志、负载变更及负责人；原因候选引用了当前等待、池满日志和负载变更，取证更全面且更快，但建议直接增加池容量、风险文字称其必要，未核实数据库承载和扩容条件。最终假设 tentative，没有独立 Reviewer。

多 Agent 只查询 db_cpu、pool_usage、pool_wait，跳过 Knowledge，未触发补查。它给出“检查配置与容量适用性”的谨慎建议，并保留配置与连接占用缺口；Reviewer 通过，但没有要求查询获取连接超时日志，也未取得负载变更。H1 所引主要是使用率，等待因果的支持引用仍有限。passed 只代表内部复核通过，不代表完整取证或真实修复成功。

与旧次多角色运行比较，本次模型调用 13→6、耗时 62.672→18.328 秒、partial→completed；单 Agent 同样出现 6→2 次模型、24.234→10.438 秒变化。这只是两次样本的观察，不能把全部变化归因于代码优化：模型输出波动和服务端模型版本未控制。

**本次结论：当前单 Agent 更快、关键观测更全；当前多 Agent 建议更谨慎且完成内部复核。尚未证明多 Agent 综合效果更好。** 一组开发案例不代表总体表现，没有为了获得有利结论扩大预算或重复抽样。

## 历史真实模型对照

已保存可公开的指标投影：[historical-comparison.json](historical-comparison.json)。不包含真实业务日志、令牌、提示词或完整模型原始输出。完整原报告仍在本地忽略目录中，原字节未修改；比较数据绑定报告 SHA-256、配置、数据哈希和源码版本。

| 维度 | 单 Agent | 多 Agent |

**观察：这组样本没有证明多 Agent 提升效果。** 单 Agent 取得池压力观测，但最终假设未引用已取得的超时日志，建议中“扩容必要”的措辞过强。多 Agent 取得负载变更与更多事实，但最终假设引用不充分，补查没有取得新观测，建议被复核拦下。四个工具尝试之外的拒绝结果不代表四次额外 Provider 请求；调用计数与拒绝事件分开记录。

Codex 已逐项辅助审阅这两份报告的十二项 F/H/A 陈述，见 [assistant-review.json](assistant-review.json)。每项保留 supported、qualified 或 insufficient 判断及理由。此为助手分析，**没有冒充人工评分**，总体准确率和费用仍为未知。

要重建本地审阅材料，在拥有原始历史报告的本机执行：

```powershell
.\.venv\Scripts\python.exe scripts/prepare_showcase_review.py --bundle output/incident-comparison-live-owner-retest/3e8db0e7-1bd9-4c15-b824-a962b68c8799/bundle.json --assistant-review examples/showcase/assistant-review.json
```

生成 `comparison.json` 和 `human-review-template.json`。人工审阅需检查全部事实、假设与建议，填写判断、理由和身份，再通过原 `evals.incident.comparison` 校验原文、引用与报告哈希。不要直接将助手意见改名为人工结果。

人工评分规则：逐项检查 F 的陈述是否符合所引来源，H 的引用是否支持其表述强度，A 的条件与必要性是否受观测支持。原因方向合理与原因已经确定分别判断；字段覆盖不直接算作语义支持。检查是否忽略正常对照、是否把历史案例当作当前原因、是否声称未验证的恢复。run 级 cause_correct、overconfident、escalation_appropriate 与每项 supported 均由审阅者填写，rationale/reason 给出依据；保留原文及引用不变。只有完成全部条目并经原评分器校验，才能计入人工指标。允许多 Agent 更差，partial 不从样本中剔除。

如之后比较当前版本，先使用已有 `scripts/compare_incident.py --plan --cases case_001 --model-budget 8 --tool-budget 8` 查看免费计划。该组总上限是 16 次模型、16 次工具尝试；实际付费执行仍需另行授权。本收尾没有发起新模型请求。

## 一个真实业务闭环

来源：本地知识库试点过程与用户在会话中的成功反馈，属于用户确认案例。公开描述使用业务概念，不公开本地登记、身份、容器名称或真实数据。

1. 用户反馈索引任务排队；当前观测出现活跃 Worker 为 0、队列深度大于 0，并取得停止事件。
2. Agent 读取工单范围内观测，形成有条件的处置建议；这些现象说明消费者缺失，不能单独证明停止的深层原因。
3. 人工选择支持动作的当前证据，创建登记目标的重启提案，检查适用条件、风险和恢复验证方法。
4. operator 审批后另行确认执行。后端执行器仅操作登记目标，检查幂等、健康和症状恢复。
5. 用户反馈修复成功，知识库文档已入库。正式闭单与检索质量未另行核验。

这是项目业务落地证据，不用于统计整体修复成功率。命令行展示还会运行模拟闭环：零真实写操作，一次模拟执行；重复相同执行请求返回原结果，不重复执行；修复 verified 后工单仍需人工确认。

## 五分钟讲解顺序

| 时间 | 内容 |
| --- | --- |
| 0–1 分钟 | 说明问题与架构：模型决定调度和工具，Harness 限制权限、预算与可信输出 |
| 1–2 分钟 | 打开正常演示，说明一条观测怎样进入事实与原因引用 |
| 2–3 分钟 | 打开补查演示，指出历史与当前证据冲突、具体检查与新观测 |
| 3–4 分钟 | 打开预算不足结果，说明 partial、停止原因、结构校验不保证因果正确 |
| 4–5 分钟 | 展示真实业务闭环与历史对照，说明多角色成本和当前限制 |

## 简历表述与面试边界

可按个人实际参与情况选择以下表述，不添加未测量的提升百分比：

- 基于 LangGraph 实现五角色故障诊断编排，支持模型选择只读工具、证据驱动诊断、逐项复核及一次有界补查。
- 构建统一执行 Harness，约束工具权限与服务范围，管理调用预算、去重和有限重试，使用结构化契约与来源引用校验保留可追溯运行记录。
- 实现人工审批与受限执行器的修复闭环，并建立同预算单／多 Agent 对照与失败案例分析；本地 Worker 恢复及文档入库由用户确认。

面试时能直接指出：模型选择工具的位置是 Investigation 循环；路由执行在 LangGraph，业务协调在 Collaboration；权限与计数在程序侧，不依赖提示词承诺。五角色不是五种模型，复核不是独立真值。对照只有小样本，尚未证明多角色准确率提升。SSE 回放不等于 checkpoint 恢复。

## 当前完成范围

三个收尾的工程材料、免费演示、机械核验、助手辅助评分与公开说明已交付。当前版本额外执行了一组经用户授权的真实模型配对；正式人工语义评分仍待使用者审阅，未用于调优的独立测试集未执行。本项目不将内部 passed 或助手意见包装成人工质量验收。

优先用现有材料投递与讲解；后续根据实际职位要求再选择一个深化方向。新增服务指标、任务查询、服务管理页面和更多修复动作暂缓。
