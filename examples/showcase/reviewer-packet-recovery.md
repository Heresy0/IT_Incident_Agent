# Reviewer 输出容量与契约一致性复验

标准 `legacy` 仍为默认，`review_driven` 需要显式启用。终版应用提交 `78bd522`，指纹 `ed732d858816af11`；每批验证前分别冻结代码、驱动、案例与原准则。新接口只用于新流程的 JSON Reviewer，不改变标准流程提示词、校验、调用方式及默认额度。

## 已确认根因

上一轮十八次回归中的新流程，九次 Diagnosis 都交付成功并进入 Reviewer，但只有一次末次有效复核。十二条 Reviewer 原始响应明确标记 `finish_reason=length`，每条恰好耗尽 2200 输出 token：这是容量限制，不能当作普通 JSON 格式错误。截断发生在七次运行，六次最终因此没有有效复核。

完整响应也有独立契约冲突：触发假设被拿来阻塞近端机制问题；远端内部信息缺口同时挂本服务读取提示；给未支持的行动添加人工任务；逐问题条目缺少 reason 或把其它字段放进 assessment。提高输出额度不能解决这些判断和字段归属错误。

还发现生成 schema 与运行时规则不一致：运行时允许非核心、非阻塞未知保留 `blocking=false` 和空 blocker，旧生成形态却要求所有 uncertain/evidence 都有 blocker。这会把不关键的未知包装成新的阻塞问题。修正仅作用于新 JSON 接口；症状、机制仍由程序固定为核心，未知仍是 uncertain，不自动变成 supported。

## 实施边界

`ReviewerFrame` 在每次复核及其一次纠正期间绑定同一组草稿目标、证据问题与登记渠道，提供精简 `ReviewerPacket`：

- 模型仍独立给出 F/H/A 和逐问题 verdict、reason、当前 EV、反证、补查、修稿及人工交接内容。建议 reason 不超过 140 字，硬上限沿用原契约：assessment 500 字、need 400 字。空数组、null 和默认字段可省略，不要求重复原稿。首版新增的 140 字硬限制确实拦截了原合同允许的文本，已撤回，失败原样保留。
- `cause_level` 从已注册问题 purpose 推导；渠道对应的 role 从登记工具绑定；`action_quote` 从本次已支持 manual_check 的当前原文绑定。这些是确定性元数据，不是模型补出的判断。原始响应与 `reviewer_packet` 绑定事件共同保留，人工任务的正文仍由模型写。
- 新流程 H 仍只允许 supported/uncertain；局部反证使用根级 counterpoints，不输出旧 refutation_basis。所有原始命题、真实字段、查询台账、人工任务对象和修稿范围校验继续执行。
- 来源提示放在 `request_evidence.source`，贴近所选单一缺口，再恢复成既有内部 `request_source`。相关 external_source blocker 与本地来源提示冲突时明确拒绝，不替模型删掉冲突、换关联目标或提升支持。
- 每个 supported manual_check 必须有人工任务；未支持行动不能附任务。程序只绑定原文，仍检验缺失字段、锚定证据、真实查询状态、完成条件和用途，不证明任务语义正确或授权执行。
- 新路径遇到 `finish_reason=length` 直接产生 `MODEL_OUTPUT_TRUNCATED`，即使局部响应看似完整也不发布；从同一原始输入最多纠正一次。实际请求、失败和 token 都计入总额度。
- 纠正提示只对新接口识别固定公共字段名，让错放的 blocker、ledger_assertions 等有精确路径；任意未知字段名和值仍隐藏。生成 schema 还明确表达已有“仅触发未知不能阻塞机制/竞争解释”的判定关系，模型仍可独立重评全部 verdict，不由程序给出语义答案。
- `NeedRowFields` 共享逐问题字段类型、来源编号及额外字段拒绝，逐问题身份与互斥形态继续独立保留。只共享字段，避免重新引入旧定义的重复条件；不会跳过原运行时校验。

精简接口最后恢复到原 `RevisionReviewDecision`，再经过原引用、范围、阻塞、来源及交接校验。没有 fuzzy 匹配、自动生成新证据或修改语义 verdict。Diagnosis 的请求内短引用恢复继续保持原实现。

## 免费检查与付费协议

首版完整测试 779 项；终版完整回归 784 项：764 通过、20 项数据库测试跳过。63 项终版定向检查通过，它们是完整回归的子集，不叠加成绩。15 份标准流程历史行为基线重复匹配。另有 81 种完整判定组合验证生成规则与现有范围门禁一致；1,296 组字段变体验证共享定义与原行内约束接受/拒绝等价，控制样本 schema 从 12,321 减到 11,508 字符。

首次两项新测试发现旧生成器重新引入已移除的 RefutationBasis 引用，修正生成器后通过；首次去重控制夹具误带核心 blocking=null，而生成接口要求省略，该控制失败也保留。直接共享旧 need 定义反而增加 454 字符，改为只共享公共字段后减少 813 字符，等价检查继续通过。所有初次与最终检查日志均保留并记录哈希。

[冻结协议](../../evals/reviewer_recovery/README.md)使用上一轮三个已见合成案例，模型自主规划、起稿、复核，不预置反馈、不回放输出、不调参重跑至通过：

| 组别 | 运行数 | Reviewer 输出上限 | Reviewer 超时 |
| --- | ---: | ---: | ---: |
| 主对照标准流程，三例各三次 | 9 | 4800 token | 60 秒 |
| 主对照新流程，三例各三次 | 9 | 4800 token | 60 秒 |
| 新流程原输出上限探针，三例各一次 | 3 | 2200 token | 60 秒 |

其余角色均 2200 token、30 秒、温度 0、SDK 不重试。每次最多 16 个实际模型请求、8 次工具、600 秒；末稿预留 3 次模型、90 秒。全批最多 336 次实际请求，失败也计费计数。额度提升只用于评测，业务默认 `build_roles` 仍 2200 token、30 秒。

两组主对照共享额度；与历史批次比较时同时改变了额度、超时、预留和新路径接口，不能把整体差异都归因于某一修复。三个原额度探针仅作描述，不是统计因果实验。作者自评、单模型和合成快照不能证明生产收益。

原评分准则保留，案例 2 只有发布完成时间，没有开始或生效时间；不据此计算严格时序排除准确率。来源合法、内部 passed、人工任务结构合法均不等于因果结论正确。

## 三批真实结果与失败分流

共完成 **30 次自主运行、130 次实际请求**，全部有 token 记录，无网络请求错误，共计输入 839,447、输出 133,925、合计 973,372 token。真实账单和生产工具成本未测，不能把请求更少直接说成费用更低。39 个契约/校验失败事件和 3 次输入预算停止全部留档；原历史档案未改写。

上一批新流程有十二条 2200 token 截断，本轮新流程各批均零截断；三个原额度探针也零截断，因此不能宣称只有提高额度才能解决。首批主对照新流程依然八次最终协议失败，且输入/输出 token 高于同期标准流程（269,519/43,946 对 254,272/32,674），没有整体成本或质量优势证据。

补充六次暴露更多真实边界：一条 Diagnosis 用字符串列表代替 refs 对象，纠正后交付有效稿；Reviewer 重复复制了只有 15 位尾段的 RD 编号，仍被 16 位契约拒绝，不能猜补；完整响应仍存在来源归属、字段结构失败。另两次 Reviewer 请求输入分别为 28,122 和 28,559 字符，在调用前被 28,000 门禁拒绝；没有产生额外 Reviewer 费用。失败也计入运行结果。

终版三例的分流：

- 消费者暂停例：有效 Reviewer 识别需要修改 H3，将已有证据纠错分流到 revise；后续 `RevisionDiagnosisSelection` 输入 35,844 字符超限，未发修稿模型请求，末稿复核未完成。此前有效复核保留在历史 reviews 中，但不能算当前末稿通过。该预算问题发生在 Diagnosis 修稿阶段。
- 只读写入失败例：纠正 claim_quote 范围后完成有效复核，支持 ro/EROFS 近端机制，保留触发未知；反证采用不足排除。人工任务列出系统/存储日志字段和窗口，但验收条件仍泛化，H 中“强制切换”的主体/过程也不是 ro 快照本身证明的事实；内部 passed 不等于所有语义正确。
- 业务重复例：纠正外部 blocker 与本地 source 混用后有效 partial，保留重试/幂等机制未知，来源失败时交接。建议偏向恢复日志和技术重试记录，仍缺订单、事件、幂等键关联及可验收业务对账条件，不能宣称解决重复结算。

作者已审阅全部三十次，核对新流程首稿短标签与原来源字段对应关系、有效复核中的人工任务与当前 A 原文绑定。结构合法和精确绑定只证明身份/范围，不能证明因果正确。标准流程的部分 passed 仍漏掉本地暂停、用429过度排除本地原因，或把发布完成时间当开始时间；不以内部 passed 计算质量准确率。

后两批是针对已观察问题的补充开发回归，不是新的同期配对比较，不替换首批失败。终版仅三个检查，不能据 3/3 曾有有效 Reviewer 推断稳定成功率。修稿上下文上限、触发与竞争机制的语义分类、反证逐字范围和人工验收条件仍有剩余问题；本轮进入收尾，标准流程继续默认。
