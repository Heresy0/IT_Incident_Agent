## 缺口归属

Reviewer 请求同时包含 N 编号与 H 目标时，程序检查已有需求用途和假设层级。触发 H 不能挂在症状、机制或替代 N 下；机制、替代 H 也不能挂在触发 N 下。模型可见 Schema 声明这一约束。若仍发生错配，只将请求的 need_id 置为 null，保留合法目标、缺失观测、所需结果和全部目标/需求评估，并记录 `review_request_scope_detached` / `REVIEW_REQUEST_SCOPE`。此处理不增加纠正调用，不猜测应该关联哪个其他 N。

不能由程序把原 N 自动支持或设为非阻塞；原 N 若 uncertain，仍要通过原有 blocker 校验和完成门禁。未知编号、错误引用、对已支持目标提出冲突请求等既有规则继续拒绝。已有合法触发 N 仍可使用，针对行动条件的 A 请求仍保留。旧 blocker 自动生成的补查请求也经过相同校验。N 与 H 的措辞是否正确分类仍由模型判断，程序不会凭文本关键词判定业务语义。

## 补查预算

初始取证按实际流程预留：首轮诊断和复核、Supervisor 规划、一次补查结果解释、修订诊断和再次复核。包含盲审时预留 8 次模型调用，不含盲审为 6 次，且不低于原收尾预留。非常小的预算仍采用原收尾预留，不承诺完整补查。

串行叶子和并行分支都使用这份剩余额度。初始阶段为补查保留一个任务位置与一个 Supervisor 决策位置，有当前观测后也为工具调度保留一个位置。声明任务优先当前 Investigation，再历史 Knowledge；同类当前任务优先症状和机制需求。无当前观测时仍先获取基础观测。

达到预留边界后转入诊断、盲审和最终复核，不把待查问题自动关闭；原覆盖门禁继续记录未执行声明检查和未评估需求。真实模型仍决定缺口是否有意义，以及具体工具、参数和下一步。一次补查上限、工具权限、时间限制、模型参数及总调用上限不变；错误输出的纠正、模型未声明的新查询或超时仍可能让预算不足，不能保证每次补查都能完成。
