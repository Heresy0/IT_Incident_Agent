# 取证执行和调度职责

默认流程采用三个模型角色：Supervisor 规划取证，Diagnosis 分析证据，Reviewer 复核结论。Investigation 与 Knowledge 保留为程序执行模块。实施前版本已提交为 `bc54595`。

## 查询执行

两类取证都要求 Supervisor 给出登记工具和精确参数。程序沿用角色、身份、服务、环境、时间范围和预算校验，执行查询并保存原始证据、查空、失败与截断状态。Knowledge 不再生成独立模型摘要，历史资料仍不能证明当前故障。

相同已尝试或已覆盖查询复用台账，失败不会自动重试。两个模块可以在原并行图中执行，分别维护分支台账，再合并原始证据；不自动补写事实或支持结论。

## Supervisor 规划范围

默认模型输入删除 need_updates 及其语义状态定义，使用较短的规划提示词。Supervisor 选择有区分价值的检查，给出 goal、need_ids、expected_value 和 checks，也可新增待评估的触发或操作条件问题。

现有问题的证据支持程度和重要性由诊断、复核阶段判断。兼容响应若附带旧证据评估字段，仍先校验其引用和权限，随后保留已有评估，不让 Supervisor 改写结论。问题 pending 表示等待语义复核，不再仅因此触发一次额外调度；缺失或失败的查询仍作为真实限制进入诊断。

这一分工减少了重复判断，也让 Reviewer 承担明确的最终评估职责。它可能增加 Reviewer 的判断负担，本轮不能证明总体质量因此提高。

## 派发前校验

补查阶段的输出 Schema 明确要求最多一个任务，Supervisor 输出校验也检查这一限制。返回两个角色的任务时，错误在原模型纠正循环内处理；通过校验后再派发。执行器继续保留最终门禁。

参数错误反馈包含工具名称与具体字段路径，例如 tasks.0.checks.0.args，帮助模型定位错误，不回显敏感参数值。没有合法新查询时应保留缺口并交接，不能靠派发错误隐藏尚未完成的调查。

## 角色纠正额度

默认 Supervisor、Diagnosis、Reviewer 全运行各最多纠正一次，不因任务、草稿版本或补查轮次重置。所有纠正仍计入原总模型调用和时间预算。报告记录各角色计数，机械核验同时检查真实纠正事件，拒绝伪造或超额计数。

旧 Agent 模式及显式 Reviewer 分阶段纠正实验保留原额度策略，报告标识实际策略。不同执行、提示词和额度配置不能作为只改变一个因素的性能对照。

## 验证结果

## 质量限制

结构性问题已有对应执行与校验机制，语义质量仍不稳定。首批磁盘场景的 Reviewer 缺口归属错误再次出现；证书场景的建议期待远端主动变更，措辞预设了尚未确认的触发原因；最终渠道失败场景仍用了两轮补查才停止。这些结果不能合并成同版本准确率，也不能证明整体效果提高。

最终渠道失败报告保留了必要未知及有效人工核查建议，符合辅助人工排查的目标。报告完成或复核通过仍不表示故障解决、唯一根因确认或操作获批。
