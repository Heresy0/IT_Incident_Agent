# 断言逐项复核与补查决策影响

> 历史实验：2026-10-11 已撤回本页的代码改造，当前应用恢复到 v6。下文实现和运行结果仍按实验当时记录保留，不代表当前功能。见[版本回退记录](rollback-v6.md)。

本轮针对两个实际问题实施：Reviewer 通过近端机制时，把无来源的客户端细节一起发布；已经支持当前机制和下一步后，继续因纯触发来源未知请求补查。此前结果保留在 [诊断审计记录](diagnostic-audit.md)，不重写历史报告。

## 已实施的控制

- 真实多 Agent 的 Diagnosis 为每个 H 提供 1～3 条 `claims`，明确 `observed`、`inferred` 或 `unverified`、是否关键以及所选来源字段。程序生成 `H1.C1` 等编号；观测和推断必须有当前观测来源。一次最多两条 H，保留原有输入和调用预算。
- Reviewer 必须恰好覆盖每个断言，分别给判定、关键性、来源与理由。支持引用只能从这条断言自己的来源选择；`unverified` 不能被提升为支持。任一关键断言未获支持，整个 H 不能通过。
- 盲审指出的每个未证实原因生成 B 编号。最终 Reviewer 必须明确它未被草稿声称、被声称但仍未证实，或已被具体当前来源解决。程序拒绝忽略 B、未知却同时通过关联断言，以及没有当前来源却声称已解决。这仍不能证明模型找对了相关断言，或所选来源真的解决了未知。
- 报告的原因文字由逐项通过的断言组装，待确认/未采纳断言另列。不会把未经复核的自由文字或解释重新混入已支持结论。未知关键断言仍可使整个机制待确认。
- `ReviewBlocker` 和独立 `request_evidence` 使用相同的 `impact` 契约：实际受影响、尚未支持的 H/A，两个不同观测结果，以及各自对应的决策和下一步。程序拒绝相同结果、完全相同决策分支、目标矛盾和把纯触发未知称为机制阻塞。
- 只有解释发生来源、当前行动不变的问题可放 `follow_ups`，在报告中作为非阻塞后续调查保留。不能将仍未解决的核心阻塞 N 藏入后续调查。后续调查提示仍校验角色和范围，但不调度工具。

程序校验来源有效性、逐项覆盖与内部一致性，不能证明字段语义蕴含断言，也不能证明用不同文字描述的两条行动实际不同。Diagnosis 和 Reviewer 仍使用同一基础模型，语义误判和相关性误判仍需评测及人工核查。支持有条件的建议不代表批准或执行修复。

## 验证方法

免费控制验证覆盖无依据的客户端细节、相邻字段冒充支持、关键断言未支持、遗漏/重复复核、阻塞和后续调查互相隐藏、非法工具提示，以及严格公共报告契约。一个完整流程控制例验证未知触发另列且无需补查；这是脚本控制结果，不是模型质量成绩。

真实模型使用当前配置 `qwen3.7-plus`，每条链路上限为 16 次模型、8 次合成只读工具、180 秒，保持原有纠正与补查上限。首次配对测试 `eval_002`、`show_101` 两个回归案例及当时尚未用于本轮调参的 `eval_004` 验证案例；后续看到其结果后，三者都按已见回归案例使用。保留集未释放，合成来源不代表生产服务，正式人工语义评分仍待完成。

首批多 Agent 均在最终 Reviewer 请求超时；同源码重试推送案例又因输入字符超限停止。随后删除逐项断言与整段原因的重复输入，保留全部原始观测；不扩大 28,000 字符上限。认证复测虽然完成，但仍将过去配置值推断为客户端令牌预期值并获复核支持，不能作为质量通过。此失败促成 B 编号的显式核对，以及更严格的对象/状态来源提示。

最终版本普通角色请求等待上限仍为 30 秒，Reviewer 为 60 秒，无新增隐式重试。外层保留原运行时间预算，超期输出拒绝通过；实际设置写入新配对的配置。由于等待参数和输入/输出提示也有变化，不能将后续结果全部归因于逐项复核。新旧源码的结果只作描述性比较。

第二批配对揭示纠正输入的另一处问题：首次 Reviewer 输入合法，但附带完整无效回复后达到 31,560 字符，无法执行预算内剩余的纠正。最终版本仅在这种超限时省略无效回复及旧对话，保留原始工单、全部当前观测、Schema 和具体错误反馈。审计记录省略字符数和 `source_rows_omitted=0`；原始输入仍超限时继续拒绝，不截断来源、不新增纠正次数。

最终应用指纹 `9f35686e3c07f680`，全量免费回归 455 项，448 通过、7 项数据库集成按条件跳过，61.909 秒。命令：`PYTHONPATH=app python -m unittest discover -s tests -t .`。其中 28 项新增断言/决策流程控制与一项 SDK 角色等待验证，不作为真实模型质量案例。

完整真实运行摘要见 [claim-decision-runs.json](claim-decision-runs.json)。原始运行保留在 Git 忽略的 `output/claim-decision-comparison/`，公开摘要记录必要的行为、预算和报告哈希。初期完成但语义有误的认证运行也保留，不剔除或改写。

## 真实结果与当前边界

本轮共保留 19 份完整真实运行，204 次模型调用计数、82 次合成只读工具尝试；包括两个源码阶段的 12 份配对报告和 7 份单独多 Agent 复测。所有原报告 SHA256 已核对，网络失败、超时、错误通过及后续拒绝都纳入记录。费用与 SDK 内部 HTTP 尝试数未知，不把这些运行叠加为更多独立质量案例。

最终源码的全部四次运行如下，其中认证重试沿用同源码、同预算，未覆盖网络失败：

| 案例 / 次序 | 状态 / 停止原因 | 模型 / 工具 | 秒 | 可确认的行为 |
| --- | --- | --- | --- | --- |
| eval_002 首次 | partial / NETWORK_ERROR | 6 / 2 | 56.563 | 调度请求网络失败，未完成复核 |
| eval_002 同预算复测 | partial / MODEL_OUTPUT_INVALID | 15 / 4 | 173.719 | 拒绝用触发未知阻塞 N3；纠正后又拒绝“仍未确认却支持关联断言”的 B2 矛盾 |
| show_101 | partial / MODEL_OUTPUT_INVALID | 10 / 2 | 140.438 | 拒绝不符合因果层级的影响目标；纠正后仍提出非法补查目标，没有发布未经有效复核的结论 |
| eval_004 | partial / TIME_BUDGET_EXCEEDED | 15 / 3 | 189.250 | 取证发生超时与引用错误；B1 矛盾被拦截，最后纠正结果迟到，未获批 |

认证和第三个案例分别将纠正输入从 30,361→26,232、29,987→25,964 字符，均未省略来源，证明这条修复在真实流程触发。程序时间预算用于拒绝迟到结果；SDK 请求完成后才检查外层期限，因此实际墙钟耗时可能超过 180 秒，不能将其描述为硬中断保证。

当前改善已证实的是逐项引用、盲审矛盾、补查层级的拦截，以及可审计的输入精简。最终三个案例都没有形成有效的完整 Reviewer 结果，所以尚不能证明未知细节的语义识别已稳定、非必要补查已经普遍减少，或多 Agent 质量胜过单 Agent。第二批单 Agent 在推送和第三个案例完成，仍有推送输出将低 CPU 样本写成“排除资源瓶颈”的过强陈述；完成状态仍不能代替来源审阅。

后续优化应优先减少 Reviewer 的契约错误和一次回复中重复的判定负担，并以冻结回归及人工语义评分检查是否同时保留了必要未知。无需为获得 completed 降低上述程序校验。
