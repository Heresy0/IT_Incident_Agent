# Diagnosis 引用交付根因与复验

本轮针对上一批Diagnosis引用错误实施局部修复，标准`legacy`流程仍为默认，新编排仍需显式启用。应用先冻结提交`762cd94`，字节指纹`9ca47fa5431cbfef`，复验协议另提交`171dbee`。本轮使用已有失败案例回归，不能称作未见验证或独立盲测。

## 根因

上一批十八次真实运行中，新编排九次有七次未到Reviewer，直接原因是Diagnosis引用契约未通过。六次发生在消费暂停和只读挂载案例，长字段引用被抄短、拼长或改成不存在的编号；一次发生在日志故障案例，将没有来源引用的查询失败写成finding。另一次已到Reviewer但纠正后仍不符合复核契约，最后一次取得有效复核后缺信息交接。原记录及哈希见[旧归档](reviewer-semantic-validation.json)，逐引用检查见[根因审计](diagnosis-reference-root-audit.json)。

例如`REF_1f3bc7952db3916131cd`不是24位字段引用；纠正后有一轮换成长度合法的`REF_1f3bc795c1cdae40947805c0`，却仍不在当前引用列表中。多轮纠正原样重复错误编号。来源注册表有合法字段选项，程序没有丢失对应证据；问题发生在模型交付选择器时。

三个层面的原因：

1. **把标识抄写负担混入推理。** 模型需要从多个实质字段的长哈希中选择、复制编号；新路径增加本地资源/配置观测后，候选增多。可确认的是记录中发生编号抄写错误，不能仅凭这批数据断言上下文长度是唯一原因。
2. **提示中的schema不是服务端强制输出。** 当前兼容接口使用JSON对象输出，能保证格式方向，不能强制模型遵守枚举或字段含义。原始Pydantic和来源注册表校验因此必须保留；关闭校验会把失败转成未经验证的引用。
3. **纠正信息不足以消除重复。** schema_mismatch主要说明路径与类型，长编号仍留在原候选；UNKNOWN_REFERENCE虽提醒选择真实REF，但要求模型再次从长编号中正确选择。查询失败也可能被当业务事实，不能给它随意补一个有效编号。

离线相似编号只用于查看抄写错误，**运行时不使用相似度匹配、不猜测字段、不替换为最近编号**。字段选择本身仍是待复核的模型判断。

## 改动及边界

| 模块 | 改动 |
| --- | --- |
| `agents/reference_transport.py` | 为每次Diagnosis请求构建冻结短标签目录，将模型可见选项映射为R001等；精确解码后恢复原REF，不修改原证据 |
| `workflow/coordinator.py` | 仅新编排的真实JSON Diagnosis启用标签，统一转换当前来源选项、owner_options及定向修稿模板/schema常量；原报告和Reviewer仍使用原证据标识 |
| `agents/role_runner.py` | 在原一次纠正额度内增加引用交付提示，不修改预算、修复次数或消息重建策略 |
| `scripts/compare_orchestration_live.py` | 新增`reference_recovery`固定十八次回归套件，绑定原案例、原准则、旧失败摘要及新源码，保留全部结果 |

标签只表示当前请求中的一个字段。请求及其一次纠正使用同一映射；补查后或下次修稿会重新构建目录，旧标签不能跨请求当作稳定证据ID。定向修稿模板与锁定常量同步转换，解码回原REF后仍按原稿范围校验。审计事件`diagnosis_reference_transport`保存标签、原REF、EV及field_path对应关系，能结合原始响应追踪选择。

只在类型化引用位置解码：findings.refs、hypotheses支持/反证引用、revision_concerns候选和escalation_ref。自由文本、证据值、EV编号、行动参数、权限和审批信息不改写。未知标签、长编号、错大小写和当前目录外标签拒绝；重复标签解码后仍由原始重复引用校验拒绝。负责人仍必须对应实际负责人来源，不能拿指标字段冒充。

查询失败、未查和空结果属于台账限制，无当前可引用观测时只放missing_information，不能用refs=[]构造finding，也不能为通过填不相关标签。该提示需要真实复验，不能仅凭提示文本宣称已解决。

标准流程保留原引用契约、原提示词和原校验。非JSON脚本模型保留历史兼容编号，不能用其控制结果代替真实短标签自主表现。短标签降低抄写负担，**不证明所选字段支持因果结论、不自动通过Reviewer，也不批准任何变更**。

## 免费验证与真实回归协议

完整回归769项：749通过、20项数据库检查跳过、零失败。58项定向检查包含引用错误、一次纠正、持续失败、来源恢复、修稿范围和历史冻结计划。另有真实JSON形态的定向修稿控制验证，标签模板及原引用一致；15份标准流程行为基线匹配。控制测试与完整回归不叠加计算成绩。

初次新测试两项断言失败：测试误把既有四次取证写成一次，又把包含主动修稿的模型夹具当作仅纠正场景。修正测试夹具及断言后通过，未据此放宽应用校验；初次日志`output/reference-transport-targeted.log`和最终日志均保留。

固定复验使用原三例，各三轮，两种流程，共十八次，真实Qwen自主规划、生成Diagnosis和Reviewer。两组同模型配置、16次模型／8次工具／360秒总预算、3次末稿预留、2200输出上限、零SDK重试；整个批次硬上限288次调用尝试，包括失败。不预置草稿、复核反馈或答案，不重放旧响应，不以补跑替换失败。应用、驱动和原案例在批次期间冻结。

原评分准则保留；第二例只给部署完成时间，没有开始或生效时间，不能据此严格排除较早故障期间的部署影响。该准则缺陷继续披露，EROFS/只读状态可单独评估。重点比较引用交付失败、有效Diagnosis与Reviewer可达性，再分别审阅语义和人工交接，不计算混合准确率。

## 真实复验结果

**本批引用交付恢复，但全流程仍未达到稳定验收。** 十八次按冻结计划全部完成，实际84次请求，均取得token用量，没有网络请求失败。新编排九次均一次Diagnosis调用交付有效稿并进入Reviewer，没有Diagnosis引用或其它契约错误；逐项检查短标签到原始来源字段的对应关系也全部一致。上一批新编排只有2/9次交付有效稿并进入Reviewer，有14个Diagnosis引用校验失败事件。这个变化仅针对已见回归案例的引用交付，不能推广为整体准确率提升。

新路径Diagnosis从上一批16次请求变为本批9次，Reviewer从3次变为17次。之前被诊断契约提前阻断的复核工作现在实际执行，失败成本也随之显现。新编排总token和耗时均高于同期标准流程，不能把请求更少说成总体成本效率更高。真实账单和生产工具成本未测。

本轮剩余失败：

- **12条Reviewer响应输出截断。** 涉及7次运行，每条都为`finish_reason=length`且输出token恰好2200，随后发生invalid_json。最终8次协议失败中，6次末次响应仍截断。没有通过补括号、重放、增加输出额度或追加复验掩盖失败；原始不完整响应和纠正尝试全部保存。
- **其它4个Reviewer校验失败事件。** 只读挂载首轮纠正后用触发H2阻塞机制N2，被`REVIEW_BLOCKER_SCOPE`拒绝；日志故障首轮出现额外字段与漏reason，第二轮先混淆本服务来源和范围外信息，纠正后又给未支持行动附任务，被拒绝。加上12个截断事件，本批新路径共16个失败事件，全部发生于Reviewer。
- **唯一有效末稿仍是partial。** 只读挂载第二轮支持EROFS/ro近端机制，并提供带窗口和用途的外部人工核查；N3仍把触发来源不清视作竞争机制阻塞，人工字段只泛称变更记录/内核日志，完成条件偏泛。原先完成时间与开始时间的准则缺陷也仍适用，不能计作严格时序反证成功。
- **引用合法不证明文字正确。** 新路径部分候选仍把指标变化说成写入失败的直接后果，把较晚完成的部署当作不能触发故障，或把已观测的消费者暂停归为trigger。第一例第二轮的解释还包含请求内R编号，须按当次映射理解，不能跨请求复用。程序只恢复类型化引用，不改写或证明自由文本语义。
- **标准内部通过也不代表答案正确。** 第一例两次passed仍未读暂停/队列观测，围绕429形成机制；其中一次把本地候选标成refuted，又把实际仅能查询工单服务的只读工具写成远端gateway查询。这些语义问题原样记录，没有用内部passed算准确率。

本轮只解决引用传输与纠正问题，没有继续调整Reviewer。应用与驱动在整批期间冻结，标准流程仍默认；下一瓶颈明确是Reviewer输出容量与契约一致性，再往后才是语义质量与人工交接具体性。本轮结果不支持默认切换或生产稳定性声明。
