# 报告后追加信息与关联诊断

用户可以在工单尚未解决、当前诊断已结束时，补充背景、反证或有来源的文本记录，再明确开启一轮关联诊断。原运行、报告、事件和预算账目保持不变，新运行使用新的 `run_id`、检查点线程和单独确认的预算。图内仍是原有七个阶段及四个模型角色。

本功能处理报告返回后的追问。运行中等待人工、LangGraph `interrupt()`、任意文件附件解析及自动恢复旧终态图均不在本次范围内。

## 前端使用

1. 在工单当前报告下找到“追加信息与关联诊断”。
2. 填写新情况或具体争议。可粘贴最多三条记录，每条填写来源名称、所属服务、带时区的观测时间及原文。页面时间按本地时间输入，提交时转成带时区时间。
3. 选择本轮执行方式；真实模型需要重新设置并确认本轮预算。上次运行的授权不自动沿用。
4. 提交后查看新报告。诊断历史中可回看任一轮报告、父运行关联及累计调用量；回看和事件重连不会启动诊断。

记录服务必须是当前工单服务或已授权依赖，观测时间须在工单窗口内。新提交与此前继承的记录均按本轮权限重新校验，权限收窄后不能继续沿用旧范围。单条原文和说明分别限 2000 字符，累计关联上下文限 12000 字符，超限会在新运行落库前拒绝。当前版本支持文本粘贴，不提供文件上传或图片解析。

## 输入来源和审阅

用户说明作为未核验背景提供给调查、诊断和最终返工修订；各阶段读取同一份冻结补充上下文。用户粘贴记录由程序补上提交者、提交时间及来源标识，形成可引用的不可变快照；前端报告和模型证据视图都保留 `user_submission / unverified` 标记。提交者不能指定证据 ID、引用值、审阅结果或批准状态。

前一轮命题只作为历史假设进入新上下文，不继承旧审阅批准。新记录进入本轮证据包后，诊断和审阅重新执行；用户不认可原报告也允许最终维持原判断。含未独立核验粘贴记录的运行不授予自动修复建议准入，人工补充不构成修复审批或人工金标。

仅有用户记录、没有工具取得的独立当前观测时，即使模型认为命题得到支持，也保留 `partial / USER_SOURCES_UNVERIFIED`，报告可以交付并明确标为“仅基于用户材料”。该约束同样适用于状态核查。负责人登记、手册和历史案例不能代替当前观测；日志、指标和变更来源可以形成独立当前观测。混合来源通过 `source_basis` 记录数量及状态，但不会把用户材料自动升级为已核验，不把工具记录的存在当作对用户陈述的证明。

关联报告按实际 `review_status` 说明复核通过、仍有异议或审阅未完成。认证、Provider、版本或恢复策略拒绝等失败结果也保留本轮提交内容与父报告关联；这只说明请求已保存，不表示这些内容已被模型采用或审阅。

关联链保留此前提交的说明和记录。普通“启动诊断”基于当前工单字段重新开始；继续利用补充记录时应使用关联诊断入口。若先修改了工单服务、窗口或其他字段，需要先基于新工单修订生成诊断，不能继续把旧报告作为最新依据。

## 存储与预算

新增入口复用原 `start_diagnosis` 准入、执行池及 `begin_diagnosis` 事务。事务锁住工单后，核验父运行属于当前用户且是最新已结束报告、工单修订与父快照一致，然后同时写入新运行、冻结补充上下文、递增工单修订号并更新最新运行。任何一步失败整笔回滚。

补充请求使用独立 `request_key`。相同请求重试返回原运行；同一编号改换内容或预算会被拒绝，避免响应丢失导致重复付费。跨进程竞争仍受同一工单行锁和既有唯一索引保护，不新增数据库表或迁移。

`config.followup_context` 保存父运行、父报告摘要、轮次及各次提交。检查点恢复从冻结配置重建此上下文；引用快照、预算扣减、单轮返工和候选报告继续使用既有机制。每轮内部语义返工仍最多一次；用户主动启动的新轮次在诊断历史中单列。

历史累计展示已交付报告的模型／工具次数与已知 Token。正在执行或用量不完整的轮次另行提示，金额保持未知，不把缺失用量记作完整零费用。

## 接口

- `POST /api/v1/incidents/{incident_id}/followups`：提交并启动关联诊断。
- `GET /api/v1/incidents/{incident_id}/diagnoses?offset=0&limit=20`：读取当前身份的运行历史及累计统计。
- 结果、事件和人工解决确认继续使用原接口。

```json
{
  "request_key": "followup-example-001",
  "execution_mode": "live",
  "model_budget": 16,
  "tool_budget": 8,
  "followup": {
    "parent_run_id": "当前工单最新已结束运行ID",
    "revision": 1,
    "note": "回滚后超时仍存在，请重新核查发布导致故障的解释。",
    "observations": [{
      "source_name": "人工导出的回滚验证日志",
      "service": "checkout-api",
      "observed_at": "2026-09-14T10:20:00Z",
      "content": "rollback completed; checkout timeout persists"
    }]
  }

```

前端若没有收到明确启动结果，会保存并重试原请求；对服务端明确拒绝的表单错误，允许修改后重新提交。
