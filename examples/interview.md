# 面试讲述简版

本页用于约 2–3 分钟介绍项目，随仓库提供。[架构导览](architecture.md)用于定位实现，[评估指南](evaluation-guide.md)用于核对数字。个人贡献应按实际参与范围表述，并如实说明已有工程基础和 AI 辅助开发。

## 主讲稿

我在已有工程基础上完善了一个故障辅助诊断项目。用户提交工单后，系统在权限和预算范围内查询日志、指标、变更及知识资料，生成带证据引用的诊断，审阅后通过前端交付。后端使用 FastAPI 和 PostgreSQL，前端通过 SSE 展示过程。当前核心是显式 Python 编排，包含调查、诊断、审阅和条件触发的质疑四个模型角色。

重构前最明显的问题是：模型取证会重复或漏查，语义审阅会误判支持范围，而复杂结构化输出中的局部错误可能阻断后续流程。此前反复补提示词、增加字段、校验关系和返工规则，修复了具体缺陷，但失败点持续转移。模型同时承担业务判断、引用维护和流程调度，程序又只能验证声明一致，无法证明声明在语义上正确。

重构时，我把确定性的权限、预算、查询台账、证据引用和发布条件交给程序，把模型任务缩小。调查每步只选择一项查询或结束；源事实从真实返回的记录生成；诊断拆成有限命题；审阅逐项绑定结论及证据版本。局部契约错误只纠正失败条目，语义返工最多一轮，证据或结论变化后重新审阅。服务接入登记可查询能力与数据语义，模型仍自主选择取证路径。

在冻结的同 Flash、同案例、同预算配对实验中，每版有 22 次端到端运行。最终结构、引用和审阅契约中断从 8 次降到 0 次，平均原生耗时从约 52.1 秒降到 28.7 秒，应覆盖观测取得从 26/38 提高到 37/38。但单列关键记录取得仍是两版各 5/6，估算费用只小幅下降约 3.5%。因此我把收益定位为流程可靠性、观测覆盖和延迟改善。

另外用 8 类可复现故障机制、每类 3 次运行评估，端到端严格根因内容正确为 21/24，关键证据取得为 24/24。这来自合成开发案例的非盲 AI 裁决，没有人工金标或生产保留集，不能称为生产准确率，也不能和前面的配对实验直接相减。

目前的局限仍是证据整合和语义审阅：取得证据不代表理解正确，审阅通过也可能遗漏时间、量纲或因果范围问题。项目定位是可追溯的辅助诊断，证据不足时保留缺口并交接人工。后续改进采用固定案例和未参与调优的新案例做单变量对照，提前约定收益与停止条件。

## 常见追问

| 问题 | 回答要点与实现 |
| --- | --- |
| 现在还是 LangGraph 吗？ | 当前是 [v2 Python 控制流](../app/workflow/v2/engine.py)；旧 LangGraph 链路已归档 |
| 是自主取证还是固定规则？ | 模型选择查询；[执行器](../app/tools/executor.py)只落实登记能力、权限、参数和预算 |
| 是 Tools 还是 MCP？ | 当前是本地 Tools；手册 RAG 作为可选检索工具接入 |
| 怎样避免返工失控？ | [语义返工](../app/workflow/v2/rework.py)最多一轮、共用总预算、旧批准不继承；结构纠正另行计数 |
| completed 就是正确吗？ | 不是；[结果分类](../app/workflow/v2/outcome.py)管理完成边界，根因内容由单独评估判断 |
| 能展示真实前端吗？ | 已有真实 Flash 与合成观测的[前端验收记录](../evals/frontend-post-retirement-validation-20261018.json)；新机器需单独准备数据库、配置和预算 |

本机更详细的复盘保留在被 Git 忽略的 `docs/`，本页不依赖那些文件。当前环境和每次验收的源码边界以[当前 v2 导览](current-v2.md)及其链接记录为准。
