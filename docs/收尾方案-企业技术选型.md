# 企业技术选型研究助手：收尾与版本保留方案

日期：2026-10-07。状态：待实施方案；本次只整理文档，没有实施下述业务功能。

后续执行范围已按用户要求收缩为轻量收尾：复用输入框和报告结构，完善覆盖/复核/结果传递、少量资料及验证，不实现独立选型表单和专用比较契约。实际交付以 [技术选型收尾说明](技术选型收尾说明.md) 为准；以下保留原方案依据。

## 1. 目标与开发顺序

先把现有 Deep Research 收敛成「面向企业 Agent 应用平台的技术选型研究助手」，完成可重复演示、可核查结果、基本工程验证与发布材料，作为求职简历的保底项目。

完成后冻结版本，在独立分支推进 IT 故障工单协同系统。原技术选型版本保留运行能力和演示材料，两个方向不同时大规模开发。

本方案是当前优先事项。此前的 [IT 工单实施方案](实施方案-IT故障工单协同.md) 保留为后续路线，不在此次收尾中执行。

成功标准：给定明确企业需求和少量候选平台，输出有来源的比较、约束检查、条件性建议、缺口及 PoC 验证步骤；遇到证据不足或调用异常，能够返回真实的有限结果。

## 2. 业务范围

首版只研究同一层级的 Agent 应用平台，不把模型、芯片、云服务、开发框架等不同层级产品混成一张排行榜。

- 默认比较 2 个候选平台，最多 3 个。
- 默认研究 3 个核心维度，允许增加最多 2 个维度，总计不超过 5 个。
- 使用明确标注的模拟企业需求；公开平台信息必须有真实来源，不能把模拟方案 A/B 当成真实产品。
- 本地单用户演示，沿用现有服务、API、数据库与前端。
- 自由研究入口保留；新增技术选型模式，不把全部通用查询强制变成选型。

三个默认维度：

| 维度 | 要回答的问题 |
| --- | --- |
| 部署与数据边界 | 是否支持企业要求的部署方式；哪些数据仍需发送到外部服务 |
| 接入与开发能力 | 能否调用目标模型和业务接口；必要集成能力有什么限制 |
| 成本与维护 | 已知许可、收费及运行依赖是什么；哪些费用和维护负担尚未确认 |

按需求可增加工作流能力或运行观测等维度，不对每个问题都扩展成全行业研究。性能、稳定性和成本若没有测量或可靠说明，应列为待验证项。

示例任务：小型 Python 团队希望部署内部 Agent 应用，要求自部署、调用内部 HTTP 接口，并控制数据外发；比较两个平台，说明候选是否满足条件、推荐前提及 PoC 步骤。

## 3. 用户输入

使用简单结构化表单，并保留补充描述，不增加需求访谈 Agent 或多轮需求管理系统。

| 字段 | 初版规则 |
| --- | --- |
| 业务目标 | 必填，描述要构建的应用 |
| 候选方案 | 2–3 个，记录具体产品名称及版本约束（如有） |
| 硬性条件 | 最多 3 项，例如必须自部署、必须调用内部接口 |
| 比较维度 | 3–5 项，使用预设维度 |
| 团队及部署条件 | 可选，不填写时显示未知，不推测人员能力 |
| 预算条件 | 可选，明确金额、币种、周期及覆盖范围；缺少信息时不声称满足预算 |
| 补充背景 | 可选，限制长度，不能覆盖服务端预算和执行规则 |

缺少核心字段时由 API/页面要求补齐。可选信息不全可以研究，但不能生成依赖这些信息的确定性推荐。

## 4. 最终产物

报告按以下顺序呈现，不要求固定长篇字数：

1. **需求摘要**：企业目标、候选、硬性条件及未提供的背景。
2. **约束检查**：每个候选对硬性条件标为「满足 / 不满足 / 未知」，附证据或未知原因。
3. **比较矩阵**：候选 × 本次研究维度，展示结论、来源及适用版本。
4. **建议与前提**：优先 PoC 候选、备选及取舍；允许暂不推荐。
5. **资料缺口与风险**：未确认能力、冲突、版本差异、费用缺口。
6. **PoC 检查清单**：下一步应验证的事项和判断标准，明确属于建议而非已经实施的测试。
7. **实际引用资料与覆盖情况**：原片段、来源地址、资料日期（已知时）及采集日期。

矩阵只能使用经过验证的结论，不能让 Writer 在表格里添加新的事实。无法确认的格子显示「未知」，不是空白，也不是自动判为不支持。

不增加模型自定权重的总分排行榜。先做硬性条件过滤，再给有前提的定性建议，避免伪精确评分。

## 5. 决策与质量规则

- 硬性条件有明确反证的候选，不可成为满足该条件的推荐方案。
- 硬性条件未知的候选，可建议进一步验证，不可声称已满足全部要求。
- 所有候选都不满足或资料不足时，允许不给出确定推荐。
- 明确区分事实、推断、建议；推断必须写出使用的企业条件和来源事实。
- 私有部署不自动等于所有数据都不外发；应分别判断应用部署与模型调用路径。
- 许可证、价格、能力描述绑定产品版本或资料时间；未知时间不编造。
- 不将不同版本、套餐或部署模式下的能力拼成一个不存在的方案。
- 冲突资料先检查版本和适用范围，未解决时保留冲突，不按来源数量投票。
- 搜索摘要不能支持未出现的细节；本地片段不能证明全文未提到某能力。
- 演示、模拟资料的限定必须保留；不宣称真实企业采用或实际收益。

运行状态继续使用 running/completed/partial/failed。completed 表示必要问题已被妥善处理，可以包含明确的未知与「暂不推荐」；partial 表示必要比较或核验尚未完成。不能把全部未知、全部空矩阵判为完整研究，也不能把格式完整当作答案完整。

问题覆盖以本次需求生成的必要研究任务为单位，不固定展开 15 个独立问题。每个任务注明需比较的候选；只回答一个候选不能认为整个比较任务已覆盖。判定需要语义复核，程序检查负责验证关联和防止无效结论支撑覆盖。

## 6. 保留现有流程

沿用现有路径：

```text
输入校验与需求整理
  → Planner 拆解必要问题和查询
  → Web / Local 并行检索
  → Evidence Judge 筛选证据
  → Analyst 形成比较结论与缺口
  → 最多一轮补搜
  → 支持性与问题覆盖复核
  → 确定性渲染报告、矩阵和运行结果
```

不重写为 Supervisor 动态调度，不接入自主工具循环。保留现有角色实例，只介绍实际执行的节点；不把未参与研究路径的 CodeWizard 计作每次运行都发挥作用的角色。

Harness 展示点：统一调用边界、预算、有限重试、结构校验、证据支持、问题覆盖、终止规则、事件记录与有限结果。当前是工作流编排的多 Agent，不宣称自主协商或完整分布式追踪。

## 7. 证据准备与 RAG 边界

不再做一个复杂 RAG 项目。继续使用现有 TXT/Markdown 入库与 Milvus 检索，不增加上传、OCR、混合检索、重排或多租户。

首版采用两类材料：

1. 博查检索摘要，用于发现来源和补充线索，保留 summary_only 标识。
2. 小型人工整理的官方资料片段，用于支撑关键能力，记录原始 URL、产品/版本、章节、采集日期、资料日期（未知则留空）、原文和适用条件。

先选择两个同层级真实平台，准备约 6–10 份短资料；名称和具体版本在实施资料准备阶段通过官方来源核实。保留合理长度的原文片段，不复制整站文档。模拟企业条件与产品能力资料分开，不能用模拟条件证明产品功能。

使用独立选型知识库集合，保留原集合；资料检索前或检索后根据候选与版本过滤。首版可用小型旁路元数据文件补足当前仅有路径的元数据；若过滤后不足，返回缺口，不放宽到无关候选。需要实际检索验证，而非只检查元数据文件存在。

沿用已有共享证据池 10 条、结论 12 条等边界作为起点。先验证「2 候选 × 3 维度」，遇到信息丢失再调整筛选与上限；不要为了填满全部矩阵而编造结论或无限增加上下文。

固定评测可直接注入片段验证分析控制，但不能据此声称 Milvus 检索或实时网络检索准确率。

## 9. 工程边界

继续使用现有预算、固定执行池、PostgreSQL 运行与事件、SSE 回放、日志及 /metrics。只修复本次发现的问题，不部署 Redis、Celery、Grafana、OTel 或多进程执行。

模型/检索故障分别记录；无证据不写事实性报告；用量拿不到时显示未知，不虚构费用。恢复页面读取与恢复工作流执行是两件事，首版只支持前者。

业务材料如记录在 PG 中，应有长度限制并避免进入完整正文日志。项目只承诺本地单用户演示，user_id/tenant_id 不构成认证。

## 10. 验证与验收

### 确定性控制与集成

保留现有控制测试、PG 隔离集成测试、资料校验和前端构建。新增测试集中在真实风险：

- 硬性条件有反证时不能推荐为满足条件。
- 候选或必要问题缺失时不能假装全部完成。
- 验证拒绝结论后，对应覆盖状态与矩阵同步降级。
- 伪造 ID/引用、无效矩阵关联、遗漏模拟限定不能进入事实报告。
- 未知能力、套餐差异、未测吞吐不能被扩大为确定事实。
- 新输入和结果通过真实 PostgreSQL 写入/读取及 SSE final 保持一致。
- 原普通研究、预算、并行计数与刷新读取路径不回归。

### 小型质量评测

保留现有 10 个模拟资料回归案例，不把它们称为真实产品选型评测。新增 6 个端到端选型案例：

| 类别 | 案例 |
| --- | --- |
| 正常 1 | 两候选有明确差异，硬性条件能排除一个 |
| 正常 2 | 均满足硬条件，根据团队条件提出有前提的取舍 |
| 正常 3 | 三候选存在不同部署/维护条件，输出完整比较和 PoC |
| 边界 1 | 必要能力与费用资料缺失，未知并限制推荐 |
| 边界 2 | 版本或套餐资料冲突，保留适用范围与未解决项 |
| 边界 3 | 检索失败或预算耗尽，返回真实 partial/failed |

固定片段负责可重复评估，至少再跑两次真实检索/本地入库演示，观察来源质量和检索过滤效果；失败也保留记录。普通成功案例与异常案例分别报告，不用不断重试后的最好一次代替整体结果。

人工逐条对照：事实支持、约束判定、比较覆盖、推荐前提和未知项。输出调用次数、已知 Token、耗时及终态。引用 ID 有效性和关键词覆盖只是辅助指标，不是准确率。

此小样本用于交付回归与错误分析；若反复按这些案例调提示，就属于开发/回归集，不能宣称独立泛化能力。评测不把答案标注注入 Agent。

### 发布门槛

1. 控制测试、隔离 PG 集成、前端类型检查与构建通过。
2. 6 个案例逐一完成人工复核，关键错误修复；正常案例比较必要项，边界案例正确限制结论。
3. 不允许出现伪造来源、跳过硬条件、无证据确定推荐及刷新重复启动等已定义控制问题。
4. 两次真实演示有记录，局限如实说明；能从运行 ID 查看保存的结果与证据。
5. README、资料来源、演示步骤、实际评测结果与代码行为一致。

不要求每次给出确定推荐，不要求每个案例都 completed，也不在缺乏实验时写性能提升百分比。

## 11. 分阶段实施

| 阶段 | 工作 | 交付与进入下一阶段的条件 |
| --- | --- | --- |
| S0 基线整理 | 审查四个代码草稿，保留差异；建立可验证开发起点 | 可运行基线、测试结果及版本保留安排 |
| S1 业务与资料 | 定义输入/输出，准备两平台真实官方片段和模拟需求 | 2 候选 × 3 维度样例；来源与未知项可核查 |
| S2 决策质量 | 完成问题覆盖、约束/比较关联、支持复核与报告 | 一个正常、一个不足案例贯通；必要结论可追溯 |
| S3 接口与页面 | 贯通请求、状态、结果、存储、SSE 与表单展示 | 浏览器演示、刷新读取和 PG 快照验证 |
| S4 验收与冻结 | 运行评测，修复问题，整理文档与演示并发布 | 满足发布门槛，冻结技术选型版本 |

预计约 5–8 个有效开发日，仅作范围估算；模型输出校准、资料获取或回归问题可能延长。先完成两候选三维度，不因第三候选和附加维度拖延首个闭环。

第一批实现限定 S0–S1：先整理基线，再确定契约与资料，不先重写 Agent 架构。

## 12. 当前工作区与 Git 保留策略

截至本次整理，当前 main 工作区包含四个未完成代码改动：

- app/mult_agents/nodes.py
- app/mult_agents/state.py
- app/mult_agents/harness/validation.py

这些覆盖检查草稿尚未配齐提示、测试、服务和页面。本次没有运行代码测试，不能宣称它们已通过。现有 IT 实施方案也仍是未提交文件。

实施 S0 时先检查最新差异，只整理本次已有草稿，不能用宽泛 reset 覆盖用户后续修改。保留草稿和工作区状态，与通过验证的稳定基线分开记录。coverage 思路可继续完善用于选型，不需要先整体推翻。

计划保留以下版本，具体分支与标签名称在执行时落地：

```text
可验证共同基线
├─ 技术选型开发 → 验收通过 → v1.0-tech-selection
└─ IT 工单开发 → 按原实施方案推进
```

用户希望的「目前版本」要明确区分为当前包含草稿的工作区快照和可运行共同基线。两者都可以保存；IT 改造优先从可验证共同基线出发，再选择性带入技术选型阶段已经测试的通用 Harness 修复。业务表单/报告无需全部迁移。

创建分支不会保存未提交内容；需要先保留实际差异、提交相应快照或明确归属，不能只建两个分支就切换。冻结标签只指向通过验收的提交，不指向未测试草稿。Git 发布时检查凭据、生成数据和知识资料的提交范围，保留适用许可证与必要归属，不伪造项目来源。

切换运行两个版本时使用独立配置及知识库集合；IT 新业务表按后续方案隔离。Git 回退不回退数据库和向量集合，禁止依赖代码分支自动恢复数据。当前仅写出策略，没有创建分支、提交、标签或推送。

## 13. 简历与演示

完成验收后可使用的定位：

> 面向企业技术选型的多 Agent 研究助手：基于 LangGraph 编排需求拆解、双路检索、证据复核与报告生成，通过 Harness 控制调用预算、重试、问题覆盖和输出质量，支持 PostgreSQL 运行持久化及 SSE 事件回放。

面试重点：为什么资料不足时返回未知；如何避免来源真实但结论失真；覆盖与状态如何一致；如何限制反思与成本；页面刷新如何读取原运行。

建议录制三个短演示：正常排除候选、资料冲突/缺失限制推荐、刷新回放原运行。不要演示未实现的动态协商、任务续跑、生产多租户或 SLA。

另一个 RAG 项目负责体现文档与检索工程，本项目体现多角色研究流程与运行控制。IT 工单版本完成后，通常替换或升级本条简历经历，而不是同时列出两个高度相关的版本。

## 14. 收尾停止条件

S4 达标后冻结。自主工具选择、动态协商、工单数据及模拟监控工具放到后续 IT 分支；高级 RAG 留在已有 RAG 项目。

初版不增加登录后台、队列、取消/续跑、自动部署、网页爬虫平台或自动执行 PoC。需要新能力时先判断是否阻碍已定义的验收，不能以「继续完善」无限延长保底项目交付。
