# 真实诊断复核与观测修复记录

日期：2026-10-09。针对运行 `d3350d7d-a369-48b3-9f2b-a010e582a3c4` 的故障修复。

## 原因与修改

该运行已成功请求模型和真实工具，停止点为 Reviewer。日志中连续两次出现
`REVIEW_TARGET_COVERAGE`，最后归类为 `MODEL_OUTPUT_INVALID`。诊断草稿包含
F1、F2、F3、H1，但复核评估编号与待复核编号不一致；运行没有保存原始模型响应，
所以不能精确断言当时是漏项、重复还是错误编号。

### 1. 完整复核与具体纠错

涉及 `app/workflow/coordinator.py`、`app/evidence/diagnosis.py`、`app/agents/prompts.py`。

- Reviewer 输入新增 `required_target_ids`，明确本轮需要评估的全部 F/H/A 条目。
- 提供给模型的 Schema 把 `target_id` 限制到本轮实际编号，评估条数与目标条数一致。
- 程序继续检查集合完全一致且每个编号只出现一次；Schema 提示不能代替程序校验。
- `REVIEW_TARGET_COVERAGE` 现在记录必需、缺失、多余、重复编号，并把这些信息发给模型纠正。
- 提示词明确：证据不足时返回 `uncertain` 和理由，不能通过省略条目表达不确定。
- 全运行仍共用一次结构纠正额度，原模型预算、工具预算和证据验证边界保持有效。
  不通过校验的内容不会被补写成通过，也不会自动恢复旧运行或无限重试。

### 2. 实际登记能力与调用前检查

涉及 `app/tools/executor.py`、`app/workflow/coordinator.py`、
`app/agents/investigation.py` 及相关中文提示词。

当前真实服务只登记了 `resource` 日志，旧运行请求 `configuration` 后得到
`LOG_CATEGORY_NOT_REGISTERED`，随后再次被派遣查询，同一请求被重复拦截。

- 工具 Schema 现在列出实际登记的日志类别；当前服务只允许模型选择 `resource`。
- 调度者与取证者收到登记的指标名称、单位和日志类别；不暴露 URL、PromQL、LogQL 或认证配置。
- 未登记指标、未登记日志类别及未配置的对应数据源，在预算预留和外部查询前被拒绝。
  连续无效请求不会消耗真实工具调用次数，也不会进入已执行查询集合。
- 调度与取证提示明确区分“渠道不可用”和“查询为空”：未登记渠道不能通过重试补齐，
  应选择其他登记能力、进入诊断或保留信息缺口。
- 重复的合法查询仍由现有 `DUPLICATE_TOOL` 规则拦截；任务、步骤和调用预算仍限制模型循环。

这些修改减少无效调度，不能保证模型永远不提出错误请求；程序仍负责拦截。

### 3. 指标采样与真实间隔

涉及 `app/tools/executor.py`、`app/providers/http.py`、
`app/providers/history.py`、`app/providers/registry.py`、`app/evidence/model_view.py`。

旧代码虽限制每指标最多 60 个采样点，但完整证据及引用目录还受 12,000 字符限制。
24 小时、多指标查询仍容易在证据封装阶段被截断。

- 真实指标查询前，按完整证据、引用目录和登记字段大小估算每指标可以容纳的采样点数。
- Prometheus 查询据此调整步长，保持每指标最多 60 点和完整结果最多 12,000 字符的边界。
- 采样网格对齐窗口末端，优先保留最新观测；不会把请求时间扩展到工单范围外。
- `granularity` 记录实际间隔，`requested_granularity` 保留请求的 `1m` 或 `5m`。
  两个字段同时进入精简模型视图。
- 后端异常多返回数据或证据仍超出容量时，继续标记 `truncated`，不会隐藏截断。
- 短窗口按请求粒度能够容纳时保留该粒度；需要细查时应缩小窗口、聚焦少量指标。

采样未截断只表示计划采样结果没有因容量被丢弃，不能表示连续历史完整，
不能排除两个采样点之间的短暂故障，也不能保证历史时段都有数据。

### 4. Prometheus 端点精度

真实只读检查发现 Prometheus 会以毫秒精度处理端点；本机微秒精度的窗口结束时间
曾被向上对齐约 0.1 毫秒，导致唯一的最新采样点被现有严格范围校验过滤。

现将开始边界向上对齐、结束边界向下对齐到毫秒，并将采样网格锚定到对齐后的结束时间。
严格范围校验保留，不通过放宽时间权限修复问题。小于一个可表示毫秒的窗口返回空结果。

## 修改后的执行流程

1. Supervisor 读取工单、已登记能力和既有查询结果，分派可执行的取证任务。
2. Investigation 选择登记工具；执行器先验证身份、服务、窗口及登记能力。
3. 合法指标查询先计算证据容量和采样网格，再只读请求 Prometheus；日志只读请求 Loki。
4. 原始证据、哈希及引用目录保留在服务端，模型收到有实际间隔的精简证据。
5. Diagnosis 生成草稿；服务端为事实、假设和建议分别分配 F/H/A 编号。
6. Reviewer 评估本轮全部编号；校验失败时得到具体编号差异，最多纠正一次。
7. 有效复核决定哪些内容可进入报告；证据缺口保留，未经有效复核不表示工单解决。
