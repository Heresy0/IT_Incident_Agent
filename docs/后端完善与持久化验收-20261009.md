## 第一阶段：持久化与恢复

修复阶段事件不再集中到最后保存：preflight_passed、action_started、action_completed、每次verification和终态分别持有工单行锁提交，提交成功后才发布阶段日志和指标。action_started未能提交时不发送写操作；提交后进程丢失时保留执行边界，恢复为manual_required，不重放。

事件新增连续seq。旧事件读取时补充序号，不改旧方案的摘要。GET列表和详情使用只读存储方法，不再为回放执行INSERT/UPDATE；新增方案详情及按after_seq/limit分页的事件接口。effective_status显示expired、source_changed或configuration_changed，保留持久化status和审批记录。

使用独立docker-compose.test.yml：项目it-incident-acceptance，端口5435，数据库incident_test，临时tmpfs。没有使用正常项目5434数据库、知识库5432数据库或现有数据卷。

PostgreSQL实际验收7项全部通过，包含原运行/工单事务、002修复迁移、跨连接并发claim、越权隔离、完整提案/审批/执行/回放、阶段序号持久化及中断恢复。新增测试第一次运行的业务断言通过，但清理阶段提前关闭连接池；已调整测试生命周期，在随后的全量执行中数据库7项无错误。验收后专用容器和网络已移除。

## 第二阶段：验证原故障症状

新增app/repairs/verification.py。每个真实修复目标必须配置1..4个symptom_checks，只引用登记指标名称，不接受客户端PromQL。规则包含operator（lte/gte/eq）、threshold及max_age_seconds（5..300秒）；单位来自服务登记。

对应指标必须登记freshness_query，返回原始数据年龄（秒），例如max(time()-timestamp(queue_depth{...}))。Prometheus查询结果的评估时间不能证明原始抓取数据新鲜，因此分别校验结果时间和数据年龄。缺失、多序列、非有限数值或过旧数据都不能证明恢复。

执行前读取症状基线：如果已经满足成功条件，返回blocked及SYMPTOM_ALREADY_HEALTHY，不做无必要重启；读取失败也不执行写操作。执行后要求平台健康和全部症状规则同时满足，才标记verified。否则按已审批的次数/间隔有限检查，最终manual_required。

修复增加180秒总时间边界，检查和等待前校验；HTTP/CLI请求仍使用自身超时，已发起的同步请求不能被强行撤回，最坏会在单次请求超时后收尾。写操作不重试，不自动回滚或再次重启。

示例services.example.json已增加queue_depth症状规则和freshness_query。缺少症状规则或数据年龄查询的真实动作不会作为Agent可用修复能力公布，方案也拒绝执行。原有纯离线演示继续允许明确标注的模拟执行器。

## 第三阶段：Docker Desktop实际执行验证

新增DockerCLIExecutor，复用已有容器ID、有效HEALTHCHECK、启动时间变化和健康恢复检查。服务端登记精确64位container_id及固定Docker context；调用已安装Docker CLI，固定argv、不使用Shell、不接受命令文本，超时10秒。Docker inspect中的Env、原始输出和stderr不进入证据、日志或接口。

原HTTP执行器保留。CLI方式无需开放Docker TCP，适合Docker Desktop本机环境。登记目标结构示例：

```json
{
  "executor": "docker_cli",
  "context": "desktop-linux",
  "container_id": "填写本项目明确授权容器的64位ID",
  "actions": ["restart_service"],
  "verification_attempts": 4,
  "verification_interval_seconds": 10,
  "symptom_checks": [{"metric": "queue_depth", "operator": "lte", "threshold": 0, "max_age_seconds": 60}]
}
```

测试只对本次专用临时PostgreSQL容器实际重启一次，Running=true、Health=healthy、StartedAt改变，执行器控制验收通过。重启前核对Compose项目标签；没有重启任何既有知识库组件。它是平台执行器实测，不是故障诊断模型质量或真实业务症状恢复成绩。

scripts/verify_docker_executor.py只定位it-incident-acceptance的postgres容器，显式调用会实际重启一次，不放入默认免费CI。后续代码将Docker context固定到服务登记，避免审批期间切换默认context改变目标；该argv变更通过定向Mock检查，没有重复重启。

## 第四阶段：回放、监控和经验复用

新增接口：

- GET /api/v1/incidents/{id}/repairs/{plan_id}：包含持久化状态、当前有效状态及审批/验证条件。
- GET /api/v1/incidents/{id}/repairs/{plan_id}/events?after_seq=0&limit=50：返回items、next_seq、has_more和状态，可轮询续读，不触发执行。

新增it_incident_remediation_stages_total，仅以固定action/stage为标签，不使用工单、方案、用户、目标或症状文本作标签。日志只记录已提交阶段及关联ID，不输出执行器原始配置和检查内容。

真实Provider现在与合成Provider共享owner-only确认经验检索。人工确认的历史案例按服务、环境、版本和用户过滤，文本进入模型前脱敏。即使两人有同一真实服务的访问权，也不能读取彼此私有确认案例。

