# 状态核查与登记补查约束

日期：2026-10-09。针对运行 `140b909d-0e2b-44f3-83ad-41b25558f958` 的后续完善。

## 问题与结果

该运行的 Reviewer 已正常执行并通过结构校验，观测为 Worker 数 1、队列深度 0。
Reviewer 对“低负载”的假设保留不确定性，并提出未登记指标的补查，实际被
`METRIC_NOT_REGISTERED` 拦截。旧报告没有明确区分状态核查与故障诊断，
补查被拒绝时又使用笼统英文提示，容易误解为执行失败或必须进行人工变更。

两种目的复用同一张 LangGraph、五个角色、证据注册表、预算、存储和只读执行器。

## 工单目的

工单 JSON 增加 `purpose`：

| 值 | 页面选项 | 行为 |
| --- | --- | --- |
| `diagnosis` | 故障诊断（原因与处理建议） | 原有取证、原因假设、独立复核和受控处置建议 |
| `status_check` | 状态核查（观测与覆盖范围） | 只生成有来源的观测和信息缺口，并复核所列观测 |

API 创建和修订、服务登记 Ticket、开发案例绑定 Ticket、运行快照都保留此字段。
未指定字段的旧记录按 `diagnosis` 处理，不根据标题或症状中的“状态”关键词猜测目的。
字段保存在已有 JSON 文档中，无需数据库表迁移。

前端单一登记服务的新工单默认选择状态核查，开发案例默认保持故障诊断。
用户可以手动切换；修改目的后须保存修订，启动按钮在目的未保存时不可用。
历史报告保持原样，修改目的不会改写旧运行。

## 状态核查的结束条件

状态核查仍走 Supervisor → Investigation/Knowledge → Diagnosis → Reviewer → Finish。
模型依照预算选择必要检查，不为解释正常数值而反复寻找根因。

- Diagnosis 的提示词与提供给模型的 Schema 要求 `hypotheses` 和 `recommended_actions` 为空列表。
- 服务端继续检查目的范围；模型越界生成原因或修复建议时触发 `STATUS_CHECK_SCOPE`，
  使用既有全运行共用的一次纠正额度。不会默默删除内容并当作通过。
- 至少需要可复核的观测；没有事实时保留 `NEEDS_INFORMATION`。
- 所列事实仍须通过 Reviewer。事实存在不确定性时返回 `partial / needs_information`。
- 通过时返回 `completed / passed`、`business_result=status_checked`，
  终止原因 `STATUS_CHECK_COMPLETED`。这些字段表示观测核查任务完成，不表示服务整体健康。
- 只有状态核查完成报告不能确认故障已解决，也不能作为修复提案的依据。
  对应接口分别拒绝为 `STATUS_CHECK_NOT_RESOLVABLE`、`REPAIR_REQUIRES_INCIDENT_DIAGNOSIS`。
  真正发现故障时，应将问题和影响补充到工单，保存为故障诊断目的后运行诊断。

报告标题为“服务状态核查报告”，保留已复核事实，省略空的原因和修复章节。
`status_check_coverage` 记录读到样本的指标、已查询日志类别、未检查登记能力及限制。
报告明确显示未查询渠道、空结果、工具错误、截断和实际采样间隔；不能排除短暂异常，
也不能把队列为零解释成整体健康。

沿用既有工单状态字段；状态核查结果落在 `awaiting_confirmation` 时，页面显示为
“待查看核查结果”，隐藏人工确认解决表单。没有新增业务状态或自动闭单。

## 登记补查约束

真实服务的 `get_service_metrics` Schema 在 `metrics.items.enum` 中列出实际可查询指标。
日志类别继续按登记值限制。当数据源或对应登记能力为空时，模型可见工具列表不包含该查询工具。
程序仍使用登记、身份、窗口和角色校验，不能只依赖模型遵循 Schema。

Reviewer 输入增加 `read_only_capabilities`，包含登记名称和单位，不包含 URL、查询表达式和凭据。
Reviewer 输出 Schema 的 `ReadOnlyCheck` 根据可用工具生成 `oneOf`：
每种工具对应自己的参数结构，指标参数也带登记枚举。提交检查时仍执行同一个
`ToolExecutor.validate_args` 预检，未登记指标不消耗真实工具调用预算。

补查拒绝报告使用具体中文原因和错误码，例如：

> 补查未执行（METRIC_NOT_REGISTERED）：补查包含未登记指标；请登记对应观测能力或选择已有指标。

对于登记服务，还会显示可用指标和日志类别。重复查询、参数错误、窗口越界、角色不允许、
数据源未配置以及缺少具体工具参数都有对应说明，不再把所有拒绝归为“human changes/experiments”。
`rework_denied` 事件保留错误码和请求工具名称；预算、一次返工及一次结构纠正额度保持有效。

## 使用步骤

1. 在原后端终端按 Ctrl+C，然后从项目根目录运行：

   ```powershell
   .\.venv\Scripts\python.exe local_run.py backend
   ```

2. 打开 `http://127.0.0.1:5174/`。前端开发服务会更新页面；未更新时刷新。
3. 对已有状态核查工单，在“核查目的”选择状态核查，然后点击“保存修订”。
4. 选择要检查的时间窗口，通常先用最近 15 分钟或 1 小时。
5. 保持当前小预算，例如模型 12、工具 8；明确授权并启动新运行。
6. 读取新报告的已复核观测及覆盖限制。旧运行继续按其原始目的和结果回放。

真实模型是否遵循这些约束，仍需用户下一次显式运行确认。登记能力不足时仍会保留信息缺口；
模式不会制造 CPU、业务成功率等未登记数据，也不会声明完整健康检查已经完成。

既有修改与历史材料保留，本轮没有提交 Git 或修改外部知识库、研究项目。
