## 角色与工具

| 角色 | 职责 | 工具权限 |
| --- | --- | --- |
| Supervisor | 根据症状、实际任务结果和预算选择派发、诊断、索取信息或升级 | 无；只能请求已注册叶子角色 |
| Investigation | 自主查询当前观测，返回带有效引用的事实及缺口 | get_service_metrics / get_service_logs / get_recent_changes / get_service_owner |
| Knowledge | 查询适用手册和已确认历史工单，返回可引用资料及适用限制 | search_runbooks / search_incidents |
| Diagnosis | 形成当前事实、原因假设、反证、待查项与附条件的建议 | 无 |
| Reviewer | 逐项判断事实/假设/建议是否受支持，提出有区分价值的补查 | 无；补查由 Supervisor 转交 |

身份、服务、环境、时间与登记依赖由服务端范围决定，模型不能扩张。
只有 Investigation/Knowledge 进入 ToolExecutor；无工具角色输出原始 tool calls 被拒绝。
历史资料在假设中作为线索，不能作为当前事实；仅历史支持的假设即使 Reviewer 自报 supported，
程序也改为 uncertain，最终假设显示 unresolved。
自然语言的语义支持仍需 Reviewer 与实际验收核查，程序引用有效不等于业务结论正确。

## 执行流程

1. 从已登记 case 和服务端 Principal 取得不可变范围，先授权，再建立一个 RunContext。
2. Supervisor 输出严格决策。子任务只能是 Investigation/Knowledge，并带窄目标及必要的已观测证据 ID。
3. 程序检查任务上限、重复目标、证据 ID、角色和剩余预算，随后串行执行。
4. 子任务拿到本任务目标、必要证据和自身工具结果，不拿其他角色完整对话。
   每次模型调用和工具实际尝试都在原 Harness 边界计数；相同角色的重复查询继续去重。
5. Diagnosis 从有界来源及选择编号形成草稿。程序展开精确字段原值、单位、时间与版本，
   给假设分配 H1 等编号；草稿中的事实只能引用当前观测。
6. Reviewer 必须覆盖每个 F/H/A 项，引用已存在的证据。空结果、错误、过滤条件与截断状态
   同时提供给诊断和复核角色，不能把空或截断样本理解为健康。
7. 补查必须指出目标假设、现有证据、缺少的观测、建议检查与预期区分价值。
   Supervisor 再判断是否派发；没有预算或请求无效时保留缺口并停止。
8. 批准补查后，仅执行一次目标角色任务；Diagnosis 修订，Reviewer 再复核。
   不允许第二轮返工。各诊断版本、复核、公开理由与请求保留在 JSON 中。
9. 程序只把受支持的事实与建议放入最终报告。未复核的假设保持 tentative，
   不支持/不确定分别为 refuted/unresolved；不会把技术 completed 等同于根因确认或工单解决。

本阶段采用小型串行协调器，活动子任务最多一个。每次允许派发一至两个角色请求，
执行顺序仍串行。没有实现并行；当前三个案例没有证明并行的收益，不为此扩大范围。

## 预算与事件

默认全局上限：16 模型、24 工具实际尝试、180 秒；取证预留 3 次模型/20 秒。
最终调度、Diagnosis、Reviewer 可使用收尾预留；结构修复也计入同一全局上限。
实际取证轮数不确定，因此派发检查只保障最低余量，不能承诺所有任务都有四步空间。
预算不足会输出 partial 和缺口，不能跳过复核后报成功。

子任务最多 4 模型步骤（含最终 JSON 与修复）；任务最多 6 个；Supervisor 最多 4 个有效调度决策；
Reviewer 最多 2 次复核；返工最多 1 轮；全运行结构修复最多 1 次。
格式失败后的修复是额外、被计数的模型请求，不扩大额度。
模型 SDK 保持原有单次尝试、连接/读超时 30 秒；不承诺严格 180 秒生产 SLA。

事件共用一个 run_id，seq 单调递增，模型/工具/任务 span 与父级关联。
任务创建/开始/完成、工具选择/结果、假设提出、质疑、补查请求、修订、每次复核和结束均可追踪。
公开理由保存在 negotiation；遥测仅发送固定类别和证据编号，不把自由查询或工单文本做指标标签。
prompt_version 包含角色提示词及模型/工具契约；证据保留原有不可变快照。
M3 事件当前只保存于 CLI JSON，尚未接入工单持久化或 HTTP/SSE。
