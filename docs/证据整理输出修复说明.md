# 证据整理输出修复说明

日期：2026-10-07。修复在本地现有分支进行；本文记录最终实现和真实验证，不把中间结果的 completed 标签直接当作验收通过。

## 1. 结果与范围

原问题为：

> 请联网研究：Dify 是否提供 Docker Compose 自部署方式？只核实这一项，以官方文档或官方 GitHub 为依据，给出来源引用；不要扩展到功能、性能或采购推荐。

最终运行 `98037b84-f055-4145-8130-58a243207c4b` 返回 completed，原问题已复核覆盖 1/1，保留两条结论，引用两条真实官方文档来源。模型仍是 qwen-turbo，每次模型输出上限仍是 2,400 Token；现有八个角色和 LangGraph 图保留。

最终代码通过 36 项控制回归、4 项独立 PostgreSQL 集成测试；16 个评测案例和 5 段人工标注资料的格式校验通过，Python 编译及 git diff --check 通过。未执行完整 16 次真实模型评测；本次未修改前端代码，也未重新做前端生产构建。

## 2. 原问题为什么失败

博查已经返回真实网页结果，但旧 WebScout 提示词要求模型再次输出每条记录的标题、链接、摘要、域名等信息。程序随后又根据 source_id 用原始检索记录覆盖这些内容，形成了没有必要的誊写。

故障运行中，网页整理首次和一次修复的输出均达到 2,400 Token 上限，且未通过 JSON 校验。输出截断是重要线索；此前未保留无效响应全文和结束原因，不能证明这是唯一根因。

网页证据整理异常后，只剩下不足以满足官方依据要求的本地片段，复核未得到可接受结论，研究最终 failed。这说明搜索请求成功与完整研究成功是两个不同的验收点。

## 3. 最终如何修复

### 3.1 证据整理与裁判只输出选择结果

WebScout / LocalRAGScout 返回紧凑结果，例如：

```json
{
  "summary": "保留与部署方式有关的来源",
  "evidence": [
    {"source_id": "WEB1_1-1", "notes": "包含部署步骤"}
  ],
  "gaps": [],
  "rejected_source_ids": []
}
```

EvidenceJudge 的审计输出也只包含 source_id、reliability_score、简短 reliability_reason，以及必要的审计标记。程序复用 `_enrich_evidence_from_raw` 补回真实标题、URL、摘要、来源类型和检索级别。网络摘要仍按既有规则保留最多 1,200 字符；这次没有增加网页全文抓取。

因此，模型负责判断哪些来源相关，Python 负责保存和关联原始证据。模型不能通过重写标题、链接或摘要更换证据内容。来源选择与语义事实复核仍是独立步骤，评分高不等于结论已被证明。

### 3.2 用类型契约约束长度与字段

`harness/validation.py` 新增 EvidenceSelection、AuditedSelection、AuditFlag；EvidenceBatch 和 Audit 改为类型化列表，并禁止额外字段。

- 单次整理、审计最多 10 条选择结果，与节点现有输入上限一致。
- 整理 notes 和审计理由最多 80 字符，总体摘要最多 160 字符。
- 不允许额外返回 snippet、url、title 等原始字段。
- 评分必须在 0 到 1 之间，审计类型使用固定枚举。
- source_id 必须非空，长度受限；随后还会检查它是否实际存在。

这些规则直接进入给模型的 JSON Schema，同时由 Pydantic 检查，提示词和代码使用同一个契约。

### 3.3 来源 ID 校验覆盖一次修复后的响应

新增 `_valid_source_selection`，检查保留与拒绝的来源 ID 均来自输入、各自不重复、两组不重叠。整理和审计节点的首次响应与一次修复响应都要经过这个检查。

第二次仍无效时，节点明确失败，不能静默接受伪造 ID，也不能把已经被裁判排除的证据重新加入。既有复核节点保留逐结论拒绝机制。

### 3.4 复核使用引文 ID，增加字段级诊断

复核提示词明确要求选择 `source_id` 和 `quote_id`，程序据此取出真实片段。代码保留旧的逐字 quote 响应兼容和原文匹配检查；模型本次任务不再需要誊写整段片段。

最后一次中间联调在 verify 发生结构校验错误，输出未到 Token 上限；未保留原无效响应，不能确认具体失败字段。利用已保存的检查点单独校准 verify 后，一次通过，输出 217 Token。新增回归复现了复制长 quote 超过兼容字段限制的情况，并验证修复反馈。

现在增加以下事件：

- `model_output`：节点、尝试序号、输出字符数、可识别的结束原因。
- `validation_failure`：JSON、Schema 或选择/引文校验类别；Schema 错误另列字段路径和错误类型。
- 既有 `validation_repair`：仍最多一次，计入模型调用预算。

字段级诊断例如 `decisions.0.evidence_quotes.0.quote / string_too_long`，不记录输入值和无效响应全文。修复请求会带这些诊断，帮助模型定位错误。原有 checkpoint 和检索状态仍会保存业务资料，不能把这项改动描述成业务内容全部不落库。

### 3.5 官方依据必须核对实际来源

中间联调还发现模型把第三方教程中的官方链接、以及 `github.com/koorlan/dify` 仓库副本当成官方依据。completed 和来源评分都不足以证明这个判断正确。

新增一个小型人工核对目录 `harness/official_sources.json`，当前范围为 Dify、FastGPT：

| 产品 | 已核对入口 |
| --- | --- |
| Dify | docs.dify.ai；github.com/langgenius/dify |
| FastGPT | doc.fastgpt.io；github.com/labring/FastGPT |

Dify 入口根据 [官网](https://dify.ai/) 与 [部署文档](https://docs.dify.ai/en/self-host/deploy/quick-start/docker-compose) 核对；FastGPT 入口根据 [官方仓库 README](https://github.com/labring/FastGPT) 核对。目录同时保存核对来源和日期。

用户明确要求官方文档/官方仓库时，程序限定检索范围，过滤实际 URL 的主机和仓库路径。GitHub fork、第三方转述、相似路径、伪装域名、带认证信息的网址和用户创建的 issue/discussion 不算已核对来源。资料文本自称“官方”或包含官方链接，不能改变它自身的实际 URL。

博查适配器增加可选 `include_domains`，转为请求中的原生 `include`；限定请求不再只依赖搜索词里的 site:。一次真实 API 请求验证了原生域名筛选能取得 docs.dify.ai 的部署页。客户端仍进行 URL 校验，GitHub 域名筛选不能替代仓库归属检查。

官方来源请求跳过无来源归属的本地笔记取证。明确限定本地的请求仍不发送网络检索；本地资料若没有可核对的官方 URL，也不能被当作官方依据。没有合格来源时返回来源缺口，未登记产品需要先人工补充入口目录。普通研究保留既有网络/本地路径。

这是一项受限的来源身份控制，不是通用的互联网官方身份识别器。目录需要维护，官方页面也可能过期；URL 匹配不等于摘要已经支持所有结论。

### 3.6 尊重否定表达与单项研究范围

旧覆盖规则可能跨分号、逗号匹配“给出来源引用；不要……采购推荐”，误认为必须给出推荐。现在按子句检查建议请求，并排除部分明确的否定表达。真正要求选型建议时，仍须有 recommendation 结论才能覆盖。

用户明确说“只核实这一项”等单项核实要求时，程序只保留原问题一个研究任务，避免 Planner 自动增加必答背景问题。检索仍可使用不同官方入口；“官方文档或官方仓库”允许其中一种有效依据，不被拆成两项必须分别完成的任务。这些是针对已观察问题的规则，不能代表完整自然语言意图理解。
