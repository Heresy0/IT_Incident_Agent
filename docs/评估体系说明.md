## 如何评分

程序检查引用 ID、正文引用、支持引文原样性、调用预算和无证据拒答；关键词只作诊断。另由图外复核者对最终报告逐项判断业务覆盖、事实正确性、引用语义支持、不确定性和禁止结论。

单次语义通过需要所有业务要求满足、全部接受结论受支持、全文正确且未知项表达恰当。程序校验通过、状态 completed、Agent 自己判断 supported，都不直接等于语义通过。反过来，partial 可能是正确拒答或原问题已经回答后多余子问题未满足，不能直接作为质量失败。

本轮由 Codex 做逐报告、逐结论的 **AI 辅助复核**，标记 `reviewer.kind=assistant`，不是人工评审或统计意义上的独立双盲评测。每个判断和原因保存在归档复核文件。人工模板仍 pending，可对争议要求和结论重新复查；修改原始内容后旧指纹不再有效。

## 实际跑出的结果

使用当前 `qwen-turbo`，8 个角色相同模型，top_p 0.8，max_tokens 2400，请求超时 30 秒。temperature 未显式设置，不能宣称确定性采样。20 个虚构案例各跑两次，共 40 次，固定资料检索，不调用博查、Milvus或 Embedding；两例记忆场景注入固定快照。

| 指标 | 本轮实测 |

| 程序校验通过 | 40/40，100% |
| AI 辅助复核完成 | 40/40 |
| 严格报告级语义通过 | **26/40，65%** |
| 标准答案覆盖率，逐报告宏平均 | 93.54% |

**质量门禁未通过**：严格语义通过率低于事先设置的 85% 阈值。覆盖率超过 90% 不足以掩盖错误结论。该结果是现状基线，不是验收通过版本，更不能写成“项目准确率 100%”。两次重复和人工合成小样本不支持生产准确率或 SLA 推断。

完整逐次结果见 [首轮报告](evaluations/2026-10-08-first.report.md)，机器摘要见 [指标快照](evaluations/2026-10-08-first.metrics.json)。原始结果与复核在 `evals/baselines/qwen-turbo-v2/`，也保留了最初的本地 `output/evaluation-v2/` 文件。没有筛掉失败运行，也没有调低阈值。

首轮在评测器最终加入生产代码哈希与结构化节点终止原因之前启动，这两个字段在归档原始结果里未补写。整轮生产代码未变化，源版本为 `8121dd4`；已有最终报告保留停止原因，汇总不从文本猜造终止代码。新运行会记录新增字段。复核模板在生成后同步到最终评分器指纹格式，原始报告和来源未改写。

## 暴露的薄弱点

1. **未提及变成否定**：q03 两次都写“B 不提供 SDK”，但资料只说 B 提供 HTTP API，不能推出没有 SDK。复核引用是真实的，语义仍错误。
2. **复核过度拒绝**：q17 两次都有“不支持私有部署”的直接证据，却把纠正错误前提的结论剔除，最终说没有证据。q12 还将“有前提的优先验证建议”按“必须证明全局最佳”处理。
3. **建议前提不完整**：q12 第一次按 PG/Docker 能力建议选 C，遗漏 Milvus；否则选 A 又没有消除 A 的 PG 维护要求。
4. **扩写无依据信息**：q05 第二次推测数据保留时间、功能复杂度影响收费；q18 第一次把一般稳定性因素归给没有写这些因素的资料。
5. **范围和信息保留**：q13 第二次遗漏 B 来源，又接受引用 C 的 B 信息缺失断言；q14 第二次将 C 也前提化为开源产品，资料没有 C 许可信息。
6. **规划膨胀与输出矛盾**：已知 C 无 OCR，Planner 仍追加实现细节问题；原问题已答却因多余问题变为 partial。q15 的旧分支事实被误拒，全文还出现当前能力明确和无法确认并存的表述。

后续优先优化否定/未知区分、纠错结论与有条件建议的复核、保留候选来源及规划范围；每项修改先在开发集验证，再用新保留集和相同资料重复评估。既有保留集一旦用于调参，就应移到开发集，不能继续声称它从未用于优化。本轮没有通过反复调提示词选择最佳成绩。

## 真实检索与记忆

另跑两次小型独立基准，均通过初始门禁：5 段虚构知识资料、8 个查询（top-3），3 条本人记忆+2 条其他用户/租户干扰记忆、3 个查询（top-2），真实 `text-embedding-v1`、Milvus 与独立测试 PG。

两次知识 Recall@3 均 100%，MRR 均 0.9375；记忆 Recall@2、MRR 均 100%/1.0。全部记忆确已索引，无索引/查询异常；向量候选和 PG 输出均未出现外用户记录。过期与已删除记录返回数均为 0。两次临时集合和随机测试租户均成功清理。第二次用于确认新增集合/租户碰撞保护后的清理逻辑，首轮也保留。

脚本开发时曾传错预算对象类型，已改为现有 `Limits` 对象后执行实测；这不是生产故障。SDK 报同步环境不能初始化异步客户端，实际测试使用同步接口并成功完成。

这个 5 段语料的 100% 只能说明小型检索链路与回归符合预期，不能写成“企业知识库整体召回率 100%”。固定记忆生成场景和真实记忆召回基准分开评测，目前没有把两者串成真实记忆检索后的生成端到端评测。

## 回归与使用

原有 56 项工程回归与新增 17 项评测器验证，共 **73 项**。本机启用真实 PostgreSQL 和 Milvus 集成；CI 的 Milvus 测试未配置服务时会跳过，不能宣称 CI 也全部连接真实 Milvus。前端本轮未改动，沿用上版已通过的构建验证。尚未推送，远端 CI 未运行。

日常使用命令见 [评测指南](../evals/README.md)。报告门禁退出码：0 通过、2 未达阈值、3 未复核、4 样本不完整。可仅重建归档报告，无需付费重跑；下一次改造时用同资料/案例/重复次数与归档结果比较。

面试可说：“我把工程控制、生成质量、检索和记忆分开评估。用 20 个标注案例各跑两次，保留输入、证据、结论、复核与预算。首轮引用 ID 全部合法，但 AI 辅助复核的严格报告通过率只有 65%，说明合法引用不能证明结论正确。评估器将这些错误挡在验收门禁外，给下一轮优化提供了明确基线。”
