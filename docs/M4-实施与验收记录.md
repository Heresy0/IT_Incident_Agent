## 执行过程

1. Bearer 身份由服务端绑定 `(tenant_id,user_id)`。创建时校验时区、窗口不超过 24 小时、发生时间在窗口内；业务字段存入 incidents.document。请求不能指定 owner 或依赖白名单。
2. 同工单启动先查 owner 和 request_key。相同键、相同模式及预算返回原 run_id，终态后仍幂等；同键不同参数返回 409。新键遇活动诊断或已解决工单返回 409。
3. 新运行占用已有执行池的一个配额。在数据库事务中锁定 owner 工单、复查幂等、插入原运行表的输入快照与执行配置、设置 latest_run_id / investigating，并写首条 status 事件。数据库另有活动运行和启动键的唯一索引防止重复。
4. Worker 选择既有研究图或故障协作 adapter。故障角色共享一个 Context，持久化回调先写事件，再给出服务端 seq。模型/工具步骤仍由原 Harness 计数，工单不读写原个人会话记忆。
5. 终态、唯一 final 事件及工单状态一次提交。completed / partial 进入 awaiting_confirmation；failed 返回 open。提交 worker 失败保存失败终态并释放配额；数据库事务失败回滚并释放配额。
6. 页面 GET 原运行结果或按 after_seq GET 原事件流。刷新、切换工单和重新连接均不 POST 新运行；启动请求先把键及额度存入当前身份 sessionStorage，丢失 202 时可重试原请求。退出身份取消前端连接；已接收的后端运行继续按预算完成。
7. 只有拥有本工单的 operator 能人工确认。确认必须匹配最新 run_id 与 revision，运行必须 completed / partial，且运行快照仍是本次修订。确认键和完整内容相同返回同一 case_id；不同内容或二次独立确认冲突。确认经验与 resolved 状态在一个事务提交。
8. Knowledge 的 search_incidents 合并人工确认经验与原合成历史，限制同 owner、服务/环境/版本、active、症状词及可选错误码，最多返回 4 条。未确认诊断不进入经验表；人工历史不能独立证明当前原因。

后端仍只支持一个进程，禁止 uvicorn 多 worker：执行池为进程内配额，启动恢复会把未结束运行标记 PROCESS_INTERRUPTED。重启后的旧运行可回放；重新诊断需要新启动键，不会自动重启模型。

## API

所有接口需要 `Authorization: Bearer ...`，不接受 URL 中的令牌。

| 方法与路径 | 作用 |
| --- | --- |
| GET `/api/v1/incident-demo-cases` | 三个中性、明确标记合成的案例字段，用于填表 |
| POST `/api/v1/incidents` | 创建工单，201 |
| GET `/api/v1/incidents?offset=0&limit=20` | 当前 owner 分页列表，limit 1–100 |
| GET `/api/v1/incidents/{id}` | 当前 owner 详情、状态、修订、最新运行 ID |
| PATCH `/api/v1/incidents/{id}` | `{revision,changes}`；changes 为完整业务字段替换；活动/已解决工单不可改，旧运行快照保留 |
| POST `/api/v1/incidents/{id}/diagnoses` | 202，返回 run_id、result_url、event_url、replayed |
| GET `/api/v1/research/runs/{run_id}` | 复用原 owner 隔离的运行结果接口 |
| GET `/api/v1/research/runs/{run_id}/events?after_seq=0` | 复用原 SSE 回放；也支持 Last-Event-ID |
| POST `/api/v1/incidents/{id}/resolution` | operator 人工确认与经验入库 |

免费启动请求：`{"request_key":"unique-start-key","execution_mode":"scripted_control_only"}`。

真实启动必须显式指定 `execution_mode=live`，同时提供 `model_budget`（6–16）、`tool_budget`（1–24）。默认上限 180 秒，保留 3 次模型和 20 秒收尾额度。小预算可能返回 partial；调用数包括 Supervisor、子任务、Diagnosis、Reviewer 与结构修复。没有真实 Key 的验证使用免费测试模型工厂，不绕开计数。

人工确认字段：`request_key,revision,run_id,confirmed_cause,resolution`，可选 `tags,error_codes`（各最多 8 条）。确认报告人工实际核实的原因与处理结果，不自动执行处置。

## 数据与迁移

- incidents：业务字段 JSONB、owner、business_status、revision、latest_run_id、时间戳。
- confirmed_incident_cases：owner、工单/运行 ID、确认键、业务快照和人工确认内容、operator_manual、active、修订、确认时间。
- research_runs.config：task_type=incident、incident_id、request_key、execution、incident_snapshot、limits、workflow_version、source_version、memory_enabled=false。具体 prompt_version 与数据/引用版本保存在结果及证据中。
- incident_schema_versions：当前版本 1。PostgresRunStore 在原运行表初始化后执行幂等 SQL；只在本项目配置的数据库运行，不调用其他项目迁移，也不回滚已提交修改。
- 两个数据库部分唯一索引分别约束同 owner/工单最多一个 running，以及启动键跨终态唯一。确认表另外限制每工单只确认一次。
- 确认经验首版使用受限词匹配，没有声称已验证 Milvus 向量召回。
