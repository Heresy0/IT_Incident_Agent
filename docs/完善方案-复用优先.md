# Deep Research 完善方案：复用优先

版本：2026-10-06（方案）。首版已于 2026-10-07 按复用优先范围完成实现，实际行为、验证与限制见 [首版调整说明](首版调整说明.md)。本文保留设计依据，具体交付以调整说明为准。

## 1. 目标与范围

保留原有技术栈、工作流、8 个角色实例、检索与记忆模块、API 和 Vue 页面，在现有执行路径增加可验证的运行控制。仍以「企业 AI 技术选型研究」作为演示场景，但不要求先改成三个角色或自主工具调用系统。

首版交付：可靠的研究报告、可执行预算、结构化运行轨迹、有限并发、运行状态与结果持久化、小型评测集和基本 CI。第一版继续定位为工作流编排的多 Agent 系统，展示 Harness 对现有工作流的控制，不宣称具备未实现的自主工具循环或断点恢复。

不先迁移目录、不升级整套依赖、不重写数据模型和前端，不增加 Redis、Celery、消息队列或观测平台。原方案中三个角色、完整任务调度、取消与恢复、网页正文抓取、文档生命周期管理均后移，按实际收益逐项追加。

## 3. 第一批必须修复的问题

1. 搜索错误分类：401/403 立即报认证问题，同一运行不对同一失效凭据继续发起搜索；空结果单独记录；超时、429 等临时错误有限重试。
2. 无证据停止：没有有效证据或没有可支持的 findings 时，返回检索情况与缺口，不调用 Writer 写事实性长报告。
3. 分析失败安全：合并重复 _fallback_analysis；JSON 解析失败不能被当作「证据充分、可以写作」。关键结构用小型 Pydantic schema 校验，最多修复一次。
4. 反思提示修正：保留 reflect 节点，使用现有 PROMPTS 中的反思提示。无需增加第九个业务角色；可在该节点用统一模型调用入口执行专用反思请求，不能仅在原 Planner 系统提示后追加一句反思要求。
5. 查询计划修正：优先使用 Planner 的查询，按子问题分配检索机会；启发式词仅做缺失项兜底；补搜去掉已经执行的相同查询。
6. 证据筛选修正：明确被排除的来源不能被后续兜底重新加入；Source ID 稳定，保留来源片段与检索层级。
7. 引用渲染修正：依据刚生成的正文提取引用，参考资料只展示实际使用的来源。非法引用不能仅删除编号后保留无依据的事实段落，应删去、限定表述或返回有限结果。
8. 重复执行修正：SSE 未取得 final 时读取当前 graph 状态并判断错误，不再次 invoke 初始 state。
9. 运行隔离：研究运行由服务端生成独立 checkpoint thread ID；保留客户端 thread_id 作为会话标识，不能让不同研究共用默认工作流状态。
10. 日志脱敏：不记录 Key 前缀、完整记忆或大段用户资料；现有输出日志保留摘要与对象 ID。

## 4. 最小 Harness：在既有入口统一执行

只增加一个小型 harness 目录，按职责组织三个模块，代码变大后才继续拆分：

```text
app/mult_agents/harness/
  runtime.py       # 模型/工具调用边界、预算、超时、错误及运行上下文
  validation.py    # 结构校验、证据/结论/引用检查、有限结果
  telemetry.py     # 事件、日志、耗时及基础指标
  embeddings.py    # 沿用 DashScope，限制重试与超时
tests/             # 确定性控制回归
evals/             # 固定资料与小型质量评测
```

复用 bind_agent 作为节点前后检查点，复用 _invoke_json_agent 作为 JSON 模型请求入口，把 direct_answer_node、write_node 的直接调用也接入统一调用助手。包装 bocha_web_search_records 与 search_knowledge_base_records，保留节点的业务处理，不重写每个节点。

预算作用于实际模型和检索调用，不只作用于图节点。框架或 SDK 的隐含重试要受控并单独记录；如当前适配器不能得到实际请求次数，明确区分 agent.invoke 次数与实际 HTTP 尝试次数，不伪装为精确统计。

通过 RunnableConfig 传递 run_id，取得该运行的独立上下文。原图有并行检索，预算预占需线程安全；不能用一个全局可变计数器混算不同任务，也不能让并行分支互相覆盖预算与错误记录。对支路汇合增加一次有意义的集成检查，确保分析不因汇合错误重复执行。

### 首版预算

| 控制项 | 初始值与口径 |
| --- | --- |
| 补搜 | 最多 1 轮，使用现有 iteration/max_iterations |
| 网络检索请求 | 全程最多 12 次，包含失败与重试 |
| 所有检索请求 | 全程最多 24 次，包含网络与本地检索 |
| 模型请求 | 最多 16 次，包含修复与支持性检查 |
| 活动时间 | 180 秒；调用有独立超时，到时停止发起新动作 |
| 终止额度 | 为检查/Writer 留出调用与时间；不够时使用确定性模板 |
| 上下文 | 限制检索条目、单片段字符数和模型输入长度 |
| 并发研究 | 最多 2 个，繁忙时明确拒绝，不增加持久化任务队列 |

这些是初始配置，不是已测得最优值。时间限制不意味着立即打断在途请求。usage 可获得时记录实际 Token，不可获得则标 unknown；费用仅在定价和用量可靠时估算。首版不将 Token 精确硬限额作为承诺。

### 质量门复用原有证据链

沿用 evidence_pool、findings、claim_map、source_index，并在边界做校验：

- 来源真实来自检索记录，不由模型新增 URL。
- findings 引用的 ID 必须存在，结论能关联到保存的片段。
- Writer 只接收可接受 findings 与对应来源；删除固定长篇字数要求。
- 有缺口时返回 partial，说明未覆盖的子问题；所有证据渠道不可恢复地失败时返回 failed。
- 原有 Evidence Judge 可复用为写作前的一次批量支持性检查，无需新增角色；该调用也占预算。预算不足时仅输出已经接受的有限结论，不跳过检查后继续扩写。

首版仍以搜索摘要和本地片段为依据，网络来源标记 summary_only，不能宣称已阅读全文。程序校验只能证明关联关系，语义支持检查需用人工标注样例校准。支持性不通过的结论移除或限定表达，不用「模型给了高分」代替事实依据。

## 5. 最小工程化，不重建任务平台

保留 /api/v1/research/run 与 /stream，响应兼容增加 run_id、status 和 run_summary。状态为 running、completed、partial、failed；首版不做取消与恢复状态机。

在 PostgreSQL 增加 research_runs 与 research_events 两张小表，复用现有数据库连接方式：

- research_runs：run_id、状态、配置与提示版本、用量、结果、错误、checkpoint thread ID、时间。
- research_events：run_id、序号、节点/调用、开始/结束或错误、耗时、简短元数据。

增加 GET /api/v1/research/runs/{run_id} 查看结果，以及 GET /api/v1/research/runs/{run_id}/events 按事件序号重连。现有 POST /stream 启动一次研究并先返回 run_id；刷新后前端读取保存的 run_id 并订阅事件，不重新提交研究问题。

将每请求新建线程改为固定执行池，提交前非阻塞获取容量，满额返回明确的忙碌响应；不能只改 ThreadPoolExecutor 而继续向它的无界队列提交。同步与流式接口共用同一容量限制。

研究执行与 SSE 客户端连接解耦，任务事件先保存后发送；断开页面不让执行线程无限等待客户端队列。客户端可以重新订阅；慢客户端的缓存有上限。

后端重启时将遗留 running 标为 failed，错误为 PROCESS_INTERRUPTED，保存已有轨迹与产物。首版能够查出中断与失败，但不承诺从检查点继续；检查点沿用，为后续恢复准备。运行状态与最终事件采用事务更新，事件用 run_id/seq 唯一约束避免重复。

结构化日志覆盖请求、节点、模型与工具，使用 run_id 和父子调用 ID 关联。记录每次耗时、错误、已知 usage、检索条数和终止原因，日志脱敏并轮转。基础 /metrics 可导出任务状态、耗时与调用错误，标签只用有限枚举，run_id 和 query 不作标签。不部署观测平台，不宣称完整分布式追踪。

前端只在现有页面增加运行状态、来源片段、错误和运行摘要的折叠区；保存 run_id，支持事件重连和结果读取。先不做管理后台、复杂任务历史页或工作流编辑器。

单用户本地部署沿用现状，前端 user_id/tenant_id 不当作身份验证。对公网部署需要另外完成登录与资源授权，不包括在这个缩短版开发周期中。

## 6. RAG、记忆与正文抓取的取舍

RAG 检索和入库原样复用。演示先准备一个固定知识集合，只导入一次；需要换资料时在明确指定的演示集合重新构建，不随意清空其他集合。README 如实保留「重复导入会追加」限制，不把未实现的幂等、版本管理与删除功能当完成。

记忆模块保留，但固定质量评测关闭记忆，避免案例互相污染。演示主线不将记忆作为来源证据，也不花时间更换后端。

正文抓取暂缓。最小版必须明确网络依据来自摘要，选择摘要或本地资料能支持的有限结论。报告质量评测若显示摘要是主要瓶颈，下一步再增加受限 fetch_page；届时必须实现目标地址、重定向、响应大小和超时检查。不能为了赶工接入无限制 URL 抓取。

## 7. 开发与验收：预计 7–10 个工作日

估算前提是外部 Key 有效、熟悉现有代码、维持单用户本地范围。实际以检查通过为准，不保证自然日截止时间。

| 阶段 | 投入估计 | 工作与验收 |
| --- | --- | --- |
| A：可靠性修复 | 2–3 天 | 搜索错误、零证据、反思、查询计划、引用、重复执行和隔离；先建立 10 条确定性回归 |
| B：Harness 增强 | 2–3 天 | 统一调用、线程安全预算、有限结果、支持性检查、结构化事件；验证到限停止和并行分支行为 |
| C：工程与交付 | 3–4 天 | 有限执行池、两张表、结果查询/SSE 重连、前端小改、指标、质量评测与 CI |

最后固定 20 条案例：

- 10 条免费确定性控制回归：认证失败、正常空结果、重试上限、非法 JSON、缺失引用、补搜/预算上限、运行串用、支路汇合、并发容量、SSE 不重复执行。每条可含多项关联断言。
- 10 条真实模型质量案例：使用固定检索资料和人工标注的支持片段，测子问题覆盖、引用有效性、支持性与调用耗时；需要外部 Key 的运行显式触发。

持久化事件重连、遗留 running 清理与最终状态更新另做 PostgreSQL 集成检查；不为简单封装写镜像测试。CI 默认运行免费回归与前端类型/构建，数据库集成可独立 job；真实模型评测与线上搜索不默认消耗额度。

确定性回归必须全部通过，引用 ID 有效性应达到 100%。语义支持率按人工标注口径报告，不预先宣称达到了 90%。旧版与改进版用相同案例、资料、模型配置做比较，必要时多次运行并记录波动。对照重点是无依据报告、失败处理、引用支持和资源使用。

交付演示：有证据的技术选型；401/无证据的明确反馈；预算耗尽的有限报告；页面断线重连而不重复调用。后台重启则展示真实中断记录，不演示尚未实现的恢复。

## 8. 什么时候再做重构

完成上述版本后，只有出现可测量问题才升级：

- 角色间大量重复调用造成成本或耗时问题：对同一案例比较三角色方案，再决定合并。
- 摘要无法支持关键结论：增加受限网页正文抓取。
- 有真实长任务与中断需求：增加取消、检查点恢复与工具结果复用，补崩溃测试。
- 文档经常更新：增加幂等导入、版本和按文档删除。
- 固定检索步骤难以回答问题：再引入模型自主选择工具的受限研究循环。

当前目标是将原工作流改造成可控制、可观察、可评测的研究应用。Harness 的工作可以落实在已有调用路径，而不以更换 Agent 数量或重写框架为前提。关于执行与评测 Harness 的区分，可参考 [Anthropic Agent Evals](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)。

求职描述与实际交付一致：首版可讲预算、异常分类、证据校验、执行记录和回归评测；自主工具调用与断点恢复完成验收后再加入项目描述。
