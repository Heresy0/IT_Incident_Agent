# 故障诊断完整性修复

日期：2026-10-09。针对运行 `81aaf8d5-439e-41b0-8066-0262e5f3e132`。

## 问题

该运行已取得真实故障证据：队列由 0 变为 1，活跃 Worker 由 1 变为 0，
期间日志记录 `indexing.worker.stopped`。但 Diagnosis 只生成事实，没有原因假设
和处理建议；Reviewer 只复核已有 F 条目，全部支持后程序仍标记 `completed / passed`。

原完成条件只检查“已有条目全部支持”和特定观测缺口，缺少诊断报告完整性校验。
因此条目引用通过被误当作完整诊断完成。

## 改动与执行流程

仍复用既有五角色 LangGraph、只读工具、Pydantic 契约、引用校验与共享预算。

1. Diagnosis 输入增加 `completion_requirements`，明确故障诊断需要
   `findings`、`hypotheses`、`recommended_actions`。
2. 简体中文提示词要求解释有证据支持的故障机制，并提供带条件、验证、风险和审批要求
   的处理建议。没有登记可执行修复能力时，仍可提出人工处理建议，`repair` 保持 null。
3. 证据不足时允许空列表，避免强制编造原因。服务端检查缺少的报告部分，并将
   `diagnosis_completion_gaps` 传给 Reviewer。
4. Reviewer 继续逐项核查 F/H/A。程序在最终结束时再次检查报告完整性、已有复核结果
   和原有观测缺口；Supervisor 的 `finish` 也复用同一判定，不能绕过。
5. 缺少当前事实、原因假设或处理建议时，输出 `partial / needs_information`，
   终止原因为 `DIAGNOSIS_INCOMPLETE`，保留已复核事实、模型已有建议与具体缺口。
   完全没有可复核条目时仍使用原来的 `NEEDS_INFORMATION`。
6. 报告为空的原因和建议章节增加明确提示，不再显示空白章节。事件记录
   `diagnosis_gate`；复核完成事件也不会把只有 F 的故障诊断标记为通过。

没有增加自动模型重试、自动补查或自动修复。一次结构纠正、一轮补查和原预算继续有效。
`status_check` 仍允许只复核当前观测，不要求原因或建议，保持
`completed / passed / STATUS_CHECK_COMPLETED` 的既有语义。

## 本次演练的合理结论

当前证据支持“Worker 停止后没有活跃消费者，索引任务留在队列中”。
Worker 为什么停止是更深层的触发原因，可以作为未确认信息保留；无需因这一缺口
省略已支持的故障机制。稀疏采样不能证明整个时间窗口内始终如此。

处理建议应是人工核实停止是否属于计划维护、检查启动条件，适用时恢复索引 Worker，
再使用新鲜指标及具体任务状态确认恢复。系统不能凭空生成容器名、路径或执行授权。
诊断完成不代表故障已解决，也不代表已经执行任何修复。

## 加载和后续使用

运行中的后端需要重启才能加载源码改动；在原后端终端按 Ctrl+C 后执行：

```powershell
cd D:\code\it_incident_agent
.\.venv\Scripts\python.exe local_run.py backend
```

端口继续读取本项目本地配置；当前前端代理使用 8002。无需重建前端或修改数据库。
以后显式运行故障诊断时，先保存 `purpose=diagnosis` 和正确时间窗口，保留小预算。
不需要再次制造故障：如需验证真实模型，可选择仍覆盖原演练的固定时间范围，
由用户明确授权一次新运行。若日志保留期已过，应保留相应缺口。

旧运行与旧报告没有改写，没有再次发起付费诊断，也没有停止或启动外部 Worker。
修复的是协作诊断链路的完成判定；独立 SingleAgent 基线没有在本次扩展。
真实模型是否按新提示形成有意义的 H/A，仍需下一次显式调用确认。
