## 2. 业务定位

## 3. 原节点与 Agent 怎么改了

图结构与原八个角色实例保留，仍是固定工作流编排。没有新增 Supervisor，也没有自主工具调用循环或动态协商。

| 原模块 | 本轮改动 |
| --- | --- |
| IntentRouter | 技术选型、比较等显式研究请求不能被快速回答绕过 |
| Planner | 提示聚焦候选与条件；程序将原始需求固定为 q1，最多再保留两个辅助问题 |
| WebScout / LocalScout | 保留取证路径；用户明确限定本地来源时，初次与补搜均不发网络请求 |
| EvidenceJudge：取证审计 | 补搜取得相同来源、相同内容时，进入共享池前去重，保留不同来源或变化后的内容 |
| Analyst | 结论关联 question_ids，输出问题覆盖、实际比较、推荐前提与未知项；优先回答原问题，减少背景堆积 |
| Reflect | 接收当前覆盖和缺口，继续最多一轮补搜，不增加循环次数 |
| EvidenceJudge：结论复核 | 独立判断支持与覆盖，检查实际引文，保留拒绝原因，允许裁剪冗余来源 |
| Writer / Finish | 仍由模型安排已有结论的章节、程序生成正文；合并重复章节，有限结果不能展示未复核的“已覆盖” |

## 4. 问题覆盖与状态控制

新增 `harness/coverage.py`，为任务分配 q1/q2/q3，以已接受结论关联验证模型覆盖判断。

- 覆盖状态为 answered / partial / unanswered。
- 模型判 answered 但没有有效 claim_ids、结论未关联该问题、同一问题重复判定时，程序降级。
- 部分支撑结论在复核中被排除时，该问题不会继续保持完整覆盖。
- 对常见中文的明确建议请求，缺少 kind=recommendation 的已验证建议时不能仅凭背景事实判 answered。此规则不是通用自然语言意图证明。
- 分析阶段的判断是暂态；复核中断时，最终结果不会把暂态 answered 当作已验证结果。
- 最终复核重新给出仍存在的缺口；清除旧的临时判断，避免旧 needs_more_research 一直锁住 partial，也不重复保留旧问题状态。

只有必要任务完成、复核通过、且没有需要限制结果的错误或终止原因，研究才进入 completed。partial 可以是正确、有用的交付；completed 不表示已做真实部署或验证所有企业能力。

问题是否语义上得到完整回答仍依赖模型和人工复核。程序关联正确不等于推荐正确。

## 5. 引文与限定控制

复核输入为每条实际证据生成 `quote_id`，如 `LOC1_1-1:excerpt`。模型选择已存在 ID，程序从该真实片段提取引文，减少模型誊抄错误。

同时兼容直接逐字 quote。未知 ID、引用与原文不一致、来源超出原结论引用范围、重复支持判断等不能通过。选择 ID 时不会修改源资料，也不会替换模型提供的冲突引文来掩盖错误。

支持性输出的结构或引文错误共用最多一次修复机会，计入原模型预算；仍不符合的条目被排除，保留原因。不增加无限重试，不把“不支持”强制修复成“支持”。

普通资料中的模拟、示例、假设等限定仍需保留。固定评测适配器则明确标记 is_simulated，程序为报告增加模拟声明和【模拟事实/推断/建议】标签，不依靠模型逐句记住声明。这个标志来自实际检索记录，不由复核模型新增。

此机制保证使用了真实输入片段和有效关联；它不能证明片段的权威性、时效性或逻辑蕴含。人工复核仍须检查错误否定、版本混用和推断过度。

## 10. 如何演示与讲述

1. 保持 Docker、后端 8002、前端 5173 运行，打开页面。
2. 先运行上面的单维度本地比较，检查原问题、来源、覆盖及调用用量。
3. 再提出未被笔记证实的总成本或网络访问要求，展示未知/有限结果。
