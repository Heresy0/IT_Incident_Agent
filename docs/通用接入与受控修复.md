## 通用数据接入

`app/providers/registry.py`定义ObservationProvider协议与ServiceRegistry。登记按tenant、允许的用户、服务、环境和精确版本匹配；依赖范围由服务端赋予。未登记的工单仍返回信息缺口。

`app/providers/http.py`实现Prometheus和Loki：

- Prometheus使用管理员登记的固定PromQL，模型只能选择已登记指标名称、工单窗口和1m/5m粒度。指标名称由登记配置扩展，无需修改全局枚举。查询应聚合为一条服务序列；多序列返回明确错误，避免混合不同资源。最多60点/指标。
- Loki使用管理员登记的固定类别查询，模型不能传LogQL或URL。最多50条；抓取51条以标记截断。只提取时间、日志级别、错误码和脱敏后的message，不输出原始日志对象。
- 查询HTTP端点仅来自服务端配置。禁止URL内凭据、跳转和非本机明文HTTP；远端使用HTTPS。认证只引用环境变量名称，不把令牌写入登记文件。请求设置5秒网络超时、10秒流读取检查和1MB响应上限。
- 负责人、变更、短手册和已确认案例可先通过登记文件维护小规模结构化记录。知识条目按版本适用性过滤，案例要求confirmed且active。未配置来源报SOURCE_NOT_CONFIGURED；显式空列表表示未找到记录，不等于系统正常。
- 元数据记录包含timestamp；负责人包含service/aliases/team/escalation；变更包含category/summary；手册包含text/versions/category；案例包含text/versions/confirmed/confirmed_at/resolution/validity/error_codes。内容进入模型前再次做字段白名单和文本长度限制。

登记配置中的PromQL和LogQL必须由管理员限定服务、环境及租户对应的数据范围。登记绑定是授权边界，不能把跨租户的宽查询登记为某个用户的观测源。

GET `/api/v1/incident-services`仅显示当前身份能访问的服务、版本、依赖和指标名称/单位，不返回查询模板、URL或认证配置。

自由工单使用已登记服务字段创建，不填demo_case_id。真实观测诊断必须显式选择live，并提供模型/工具预算；scripted_control_only对自由工单返回LIVE_DIAGNOSIS_REQUIRED，不用固定案例脚本冒充真实诊断。

## 服务登记配置

将`examples/services.example.json`作为结构参考。创建本项目的`services.local.json`，填本项目身份、真实版本、服务标签和端点。该本地文件已加入.gitignore。不要覆盖现有配置或从其他项目复制密钥。

在本项目环境中设置：

```powershell
$env:INCIDENT_SERVICES_FILE='D:/code/it_incident_agent/services.local.json'
```

配置在后端创建时加载，改动后需重启本项目后端。未设置该变量时登记为空，真实修复目标默认不可用。示例里的服务、用户、查询、容器ID和域名都是占位值，不能直接作为真实环境验收。

## 修复动作与执行器

`app/repairs/contracts.py`定义restart_service、scale_service、rollback_release的参数、影响和回退约定。scale限制1..10副本且不得超过目标登记上限，rollback必须属于登记的允许版本。动作目录的存在不代表每个平台都支持该动作。

本轮真实实现仅为`DockerExecutor`的restart_service：

1. 容器目标由服务端登记，使用精确64位容器ID，模型不能选择Compose目录、Shell命令或任意容器。
2. 执行前读取容器状态，核对ID及有效HEALTHCHECK；暂停、正在重启或缺少健康检查时阻止执行。
3. 只发一次Docker restart请求，停止等待参数由代码固定为3秒。写请求超时不重试，因为服务可能已经执行重启。
4. 检查容器ID、Running、StartedAt变化和Health=healthy。仅Running或HTTP成功不算修复成功。
5. 验证预算默认3次/间隔1秒，服务端可登记1..6次及1..10秒间隔。示例为4次/间隔10秒，适配需要等待健康检查的容器；预算显示在待审批方案中。

Docker执行器使用既有Docker兼容HTTP接口或受控代理；本轮不会开启Docker TCP、修改Docker Desktop设置或暴露Docker Socket。Windows命名管道、Unix Socket、mTLS证书参数和Kubernetes尚未实现。远端接口要求HTTPS，默认校验证书，可通过登记的authorization_env引用本项目单独授权凭据。

扩缩容和回滚当前完成动作契约、参数边界和执行器注册机制，Docker执行器明确拒绝，不伪装为已执行。新增平台执行器实现name/live/actions/verification以及preflight、execute、verify；只通过后端注册，不提供动态导入、任意脚本或模型自由执行入口。

## Agent候选与审批接口

真实Provider只向Diagnosis暴露已注册且执行器支持的动作、目标、参数范围、影响及验证条件。RecommendedAction可携带repair结构；程序检查动作/目标、当前观测证据及参数，Reviewer复核后结果才保留。普通文字建议仍兼容；不能自动解析文字并执行。

API均沿用Bearer身份和工单owner隔离：

| 方法和路径 | 用途 |
| --- | --- |
| GET /api/v1/repair-actions | 查看标准动作定义，非环境支持能力承诺 |
| POST /api/v1/incidents/{id}/repairs | 从已复核诊断人工创建结构化方案 |
| POST /api/v1/incidents/{id}/repairs/from-recommendation | 从已复核结构化候选生成方案，action_index从0开始 |
| GET /api/v1/incidents/{id}/repairs | 回放方案和审计事件 |
| POST /api/v1/incidents/{id}/repairs/{plan_id}/approval | operator确认digest及approve/reject |
| POST /api/v1/incidents/{id}/repairs/{plan_id}/execute | operator显式执行，携带request_key |

手工方案字段为request_key、revision、run_id、action、target、parameters、evidence_ids和reason。例如restart的parameters必须为空，evidence_ids必须引用本次诊断的当前观测，不能仅用历史经验。

审批body为`{"digest":"方案返回的64位摘要","decision":"approve"}`；执行body为`{"request_key":"execute_001"}`。方案绑定工单revision、最新run、证据、服务登记指纹和执行器属性，15分钟过期。源工单、最新诊断、配置或执行器变化后旧批准失效，需要新方案。只有工单owner的operator可以审批和执行；普通用户只能提案和回放。模拟诊断禁止绑定真实执行器。

状态为pending_approval → approved/rejected → executing → verified/blocked/manual_required。执行前持久化claim，重复相同键只回放；换键也不会再次执行同一方案。后端最多并发2个修复；执行中的工单禁止修订、重新诊断和确认。写操作最多一次；验证有固定预算。重启不能撤销，失败转人工；扩缩容/回滚恢复需要新的明确审批，不自动循环处置。

## 存储和崩溃处理

复用当前RunStore及连接池。新增002_repairs.sql，创建独立incident_repairs表，不改已有工单或运行表字段。每个工单保存最多100个方案和阶段事件，事务持有工单行锁；内存测试存储使用同样的状态转换和锁规则。方案、审批、claim、最终阶段结果都持久化。

进程中断时executing方案启动后转manual_required，不重放写操作。外部动作与数据库不可能成为一个原子事务：如果写操作完成但结果保存失败，仍需要人工确认。中途检查结果在最终事务写入，claim之外的中途事件不能保证在崩溃前已保存。沿用单进程后端限制，不宣称分布式执行或恰好一次外部写入。

验证通过不自动关闭工单；继续调用既有resolution接口由operator确认实际原因和处理结果。真实修复确认后才能形成正式经验。
