| 类型 | 原案例 | 新案例及区分点 | 必要检查与反证 |
| --- | --- | --- | --- |
| 依赖异常 | case_001，依赖不可达 | case_004，部分业务响应超过读取期限，TCP 连接和健康检查正常；部署晚于首次错误 | 超时 WARN、健康 INFO、依赖错误率、延迟、读取期限；不能声称全部不可达或以后发生的部署造成更早的故障 |
| 配置错误 | case_002，audience 错误 | case_005，auth_mode 被设为 anonymous，而 audience 正确 | 认证模式错误日志、模式/audience 配置、健康对照；401 不等同依赖中断，也不能套用历史 audience 原因 |

新案例各包含故障前后多个指标采样、日志、配置/部署时间线、负责人、手册和已确认历史线索。标题保持中性。gold 存放在 evals/incident/gold，仅离线检查和人工核查模板读取，运行输入只包含工单及实际工具返回的快照。check_fixtures 核对单位、时间线、反证与分离关系。

目录 API 和工单输入契约接受六案例；页面通过现有目录自动提供这些选项。没有新建产品页面，也没有新建执行池或存储。新增 case_005 已通过现有 M4 创建、启动和结果读取流程的免费检查。脚本按症状选控制分支，能适配工单创建后的业务 ID。

## 实现与调用流程

| 文件 | 用途 |
| --- | --- |
| fixtures/incident/case_004–006.json、catalog.json | 新增当前观测与中性目录项，保留旧案例 |
| evals/incident/gold/case_004–006.json、manifest.json、check_fixtures.py | 独立答案、必要观测/禁止断言、集合划分和资料检查 |
| app/mult_agents/incident/single.py | 单 Agent 基线，委托已有 Investigation 循环；同六工具、同诊断输出契约 |
| app/mult_agents/incident/diagnosis.py、collaboration.py | 提取原协作的确定性引用展开与诊断校验，单/多共用 |
| investigation.py、tools.py、contracts.py | 注册 single 角色及六工具权限，终结输出可使用预留额度；原 Investigation/Knowledge 的四/二工具及四步限制保留 |
| collaboration_fake.py、scripts/investigate_incident.py | 新案例免费控制替身；原 M2 live 的 3 模型/6 工具限制保留 |
| scripts/compare_incident.py | 默认仅计划，显式 fake 免费运行，显式受预算限制的 live 入口；逐案例单/多成对保存 |
| evals/incident/comparison.py | 离线机械汇总、人工语义评分，校验报告/gold 哈希、成对完整性及预算一致性 |
| tests/test_incident_comparison.py、test_incident_api.py、CI | 免费边界回归、新案例工单集成；CI 不请求付费模型 |

1. 对照入口固定案例、模型设置和一份 Limits。每案例的 single/multi 各创建全新的同范围 Provider、模型和 Context，避免对话和运行预算跨案例共享。
2. SingleAgent 使用原 Investigation 显式工具循环。可以选择六个只读工具，身份、服务、环境、时间和知识适用范围继续由原 ToolExecutor 检查。最多 16 个全局模型步骤，随模型预算缩小；保留三次模型/20 秒供结束输出或一次结构修复，预留阶段不能执行新工具。输出采用 DiagnosisSelection 并展开真实引用，假设保持 tentative，review_status=not_performed。
3. 多 Agent 沿用原 M3 Supervisor/Investigation/Knowledge/Diagnosis/Reviewer 串行协作。各子任务最多四步，任务数量、调度、一次返工和两次复核等原限制保留。两边使用相同全局模型/工具/时间/输入上限、只读工具、诊断引用校验，以及 temperature=0、max_tokens=2200、max_retries=1、request_timeout=30 的真实模型配置。
4. 每次实际模型调用、工具尝试及重试继续由原 Harness 计数。执行结束后保存原始事件、快照、输出、计数和错误，再由离线模块读取 gold。意外失败也保存报告并进入分母；不补跑或挑选最好一次。
5. 新 UUID 目录保存 bundle.json、各 run_id.json、comparison.json、review-template.json。bundle 绑定实现内容指纹、Git 起点、未提交状态、案例快照哈希、报告哈希和配置；gold 哈希只在全部执行之后记录。当前运行数据在被 Git 忽略的 output/ 中，首次未通过的控制运行也保留。

SingleAgent 是评估基线，没有作为新的 Web/API 工作流开放。它与多 Agent 共用工程能力，区别是是否存在独立调度、知识角色和复核。脚本模型只验证协议与控制路径，工具选择不是自主行为；脚本调用数量和耗时不能作为真实模型成本或性能结论。

## 汇总与人工核查

机械检查包括事件顺序与 run_id、一致的逐步计数、快照哈希、引用字段/值/单位/时间/版本、诊断契约及预算。必要检查覆盖单独记录：它只表示字段或错误码实际返回过，不能证明采样足够、自然语言得到支持或原因正确。

真实报告的 cause_accuracy、overconfident、escalation_appropriate 和 claim_support 需要人工核查。模板列出每个事实、假设和建议，以及独立 gold 的预期原因、必要检查和禁止断言。人工填写 approved=true、reviewer、rationale、三个布尔判断和全部 claim_assessments 的 supported/reason；保留原始文本和引用。缺项、重复 ID、哈希不符或被改写的文本会被拒绝。

脚本结果始终为 excluded_scripted，不接受人工批准进入真实业务评分。没有人工核查的真实报告保持 manual_review_pending；已核查分母和总 live 分母分别展示，不把部分核查包装成全部通过。费用未测得时保留 null，token 不完整时保留原 Harness 的 unknown 状态。

