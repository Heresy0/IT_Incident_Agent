## 改动与执行流程

本轮处理 case_003 真实对照暴露的事实来源错配、遗漏 CPU 对照、重复排查三类问题，复用现有 Investigation 循环、六个只读工具、Harness 和协作调度，没有新增第二套 Agent 或重写页面。

1. **事实文本由所选来源字段生成。** 新增 `app/mult_agents/incident/observations.py`，在既有严格引用校验之后，将 Finding.statement 生成为实际指标名、聚合方式、字段值、单位和观测时间，或实际日志/变更类别与字段值。选择 pool_usage 的引用只能生成池使用率事实，不能写成 DB CPU；scaling 的 summary 明确标注 scaling，因果和“正常阈值”不能混进程序生成的事实。前后比较需要模型选择两侧引用，程序只展示实际选中的样本，不自动补造变化结论。模型继续负责引用选择、假设和建议；多 Agent 仍由 Reviewer 判断解释是否成立。
2. **新任务复用已查证据和查询结果。** Supervisor、Diagnosis、Reviewer 能看到查询状态及观测缺口。后续 Investigation/Knowledge 除调度指定的引用外，自动接收该角色已注册证据的摘要，指定证据优先，摘要总字符上限为 min(6000, input_chars/4)，查询记录最多携带最近 12 条。每个任务仍使用新对话，身份和范围仍由服务端绑定。空查询、截断和重复拒绝保留，不当作新观测。
3. **没有新信息时结束继续取证。** 对已存在证据的运行，一批普通取证任务执行后若没有新增证据 ID，记录 collection_stalled 并进入 Diagnosis/Reviewer。先完成同批次内独立任务，不因前一个 Investigation 无进展而跳过 Knowledge。已有精确工具去重继续在 Provider 执行前拒绝重复查询；重新措辞任务目标不会使系统无限继续排查。Reviewer 仍可在既有一次返工额度内请求有区分价值的补查。
4. **连接池归因缺 CPU 时保留缺口。** 当前观测中出现 pool_usage、pool_wait 或 POOL_ACQUIRE_TIMEOUT，且有原因假设却没有 db_cpu 时，取证循环最多发送一次聚焦检查反馈。该反馈不是自动执行工具、不是结构修复；后续模型和工具调用照常计入原预算。若模型不检查、预算不足或最后一步仍缺该观测，输出明确缺口且状态为 partial。多 Agent Reviewer 即使接受该原因，程序也将其降为 uncertain，最终假设为 unresolved。DB ping 不代替 CPU 观测。取得 CPU 数值也不自动证明数据库健康或扩容可行。
5. **审计与边界保留。** 新运行记录 fact_rendering=source_fields_v1 和 coverage_gaps；工单实现指纹加入新模块。引用编号协议、旧 literal 引用的严格校验、全局一次结构修复、步骤上限、预算预留及角色权限不变。提示词同步要求在假设中解释观测、引用反证、优先有用的只读补查，并保留扩容适用条件和人工批准要求。

执行路径仍是：工单 → Supervisor 调度 → Investigation/Knowledge 自选只读工具 → 引用校验及来源事实生成 → Diagnosis → Reviewer → 最多一次补查修订 → 有界完成或保留缺口。SingleAgent 复用同一取证与诊断引用展开流程，假设仍为 tentative，没有独立 Reviewer。
